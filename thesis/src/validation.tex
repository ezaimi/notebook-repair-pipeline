\chapter{Validation and Evaluation}
\label{chap:validation}

This chapter reports the evidence behind every claim this thesis makes
about its own system, in increasing order of scale.

It starts with the automated test suite, which checks each component's
logic in isolation against mocked external systems. It then reports the
real-system pilots: small, hand-picked runs that check whether the same
components behave correctly against the real PyPI registry, a real Ollama
model, real Docker execution, real GitHub repositories, and the real
Morph-KGC mapping engine. \Cref{sec:v-i7} extends these to the
orchestrator driving several components together in one unattended pass.

\Cref{sec:v-final-eval} then reports the thesis's final evaluation: the
final frozen implementation of the same orchestrator, run over the
complete 187-row evaluation split (\Cref{chap:problem-dataset}) with
Gemma-2 9B. Its explanation results (\Cref{sec:v-final-explanation})
together with the human study in \Cref{sec:v-human-eval} answer RQ1; its
repair results (\Cref{sec:v-final-primary} to
\Cref{sec:v-final-interpretation}) answer RQ2, keeping targeted-error
resolution and full notebook recovery apart.
\Cref{sec:v-model-sensitivity} repeats the evaluation with the language
model replaced by Qwen3.6-35B-A3B-MLX-8bit and answers RQ3.
\Cref{sec:v-threats} states what all of this does and does not license
concluding.

Dataset preparation has no dedicated automated test file of its own.
Instead, its output is checked a different way: the counts in
\Cref{chap:problem-dataset} are recomputed directly from its output
files. They agree exactly.

Across these areas, the tests specifically check:

\begin{itemize}
\begin{sloppypar}
  \item rejection of malformed or schema-invalid model output;
  \item rejection of a repair proposal that invents a package name or a
        version outside the retrieved evidence;
  \item the shell-safety checks from \Cref{sec:m-fixapply}, including a
        static check that \texttt{shell=True}, \texttt{os.system},
        \texttt{eval}, and \texttt{exec} never appear anywhere in the
        components that build or run a command;
  \item the three-outcome classification logic, including the
        conservative same-error check;
  \item cleanup behaviour under both success and failure; and
  \item for ResultLogger, rejection of an ambiguous duplicate explanation
        record, and correct separation of two repair attempts that share
        the same \texttt{notebook\_execution\_id} into two distinct rows.
\end{sloppypar}
\end{itemize}

All of these tests run against mocked subprocesses, a mocked Ollama
endpoint, and mocked HTTP responses. This is deliberate, and it is also a
limitation. A mocked test can prove that a component's logic is internally
consistent. It cannot prove that the component behaves correctly against
a real operating system, a running Docker environment, or a real network;
\Cref{sec:m-fixapply-bugs} showed three real bugs that a mocked test could
not have caught. The pilots below check exactly that.

\section{RAGRepairAgent Against Real PyPI and a Real Model}
\label{sec:v-i4}

\subsection{Retrieval Against Real PyPI}

The five import names used in the original retrieval-design check
(\texttt{sklearn}, \texttt{umap}, \texttt{pkg\_resources}, \texttt{scipy},
\texttt{dms\_variants}) were re-checked against the real
\texttt{retrieve()} entry point and the live PyPI registry. All four
mapped names resolved to their real PyPI distributions, with plausible,
current candidate versions. \texttt{dms\_variants} has no verified
mapping; it returned \texttt{mapping\_unknown}, and no PyPI request was
made. This confirms under real conditions that an unmapped import never
reaches the network.

\begin{sloppypar}
A second check, made during the implementation of RAGRepairAgent,
extended the mapping table by two entries. \texttt{cv2} and
\texttt{skimage} are among the frequent failing modules of the working
dataset (\Cref{tab:pd-top-modules}), and neither had an entry in
\texttt{config/}\allowbreak\texttt{package\_mapping.yaml}, so the
retriever returned \texttt{mapping\_unknown} for both. Their
distributions are generic, well-known import-to-distribution
correspondences, not information derived from any evaluation outcome.
The entries \texttt{cv2: opencv-python} and
\texttt{skimage: scikit-image} were added on 2026-08-23, checked against
the real PyPI registry, and confirmed by a regression check that the
existing \texttt{sklearn} mapping still resolved correctly. The mapping
table has not changed since: it was frozen with the rest of the
configuration on 2026-09-12 (\Cref{sec:v-final-manifest}), before the
final runs, and no entry was added in response to a final evaluation
result (\Cref{sec:v-final-pypi}).
\end{sloppypar}

\subsection{Repair Proposals Against a Real Model}

A small pilot ran \texttt{rag\_repair\_agent.py}'s real entry point, using a
real local Ollama model, in four pilot runs:

\begin{itemize}
  \item An excluded, \texttt{system\_library} record correctly abstained
        with zero PyPI or Ollama calls, confirming the eligibility gate
        works under real conditions.
  \item A \texttt{missing\_package} record (\texttt{sklearn}) timed out
        twice under the initial 120-second limit, then succeeded at the
        first attempt once the limit was raised to 300 seconds. This is
        the evidence behind the timeout change reported in
        \Cref{sec:m-repair}.
  \item The same record, rerun at 300 seconds, produced a schema-valid,
        grounded proposal: install \texttt{scikit-learn}.
  \item A \texttt{wrong\_version} record (the \texttt{scipy.integrate.cumtrapz}
        case from \Cref{tab:m-compat}, traced in full in
        \Cref{sec:m-worked-example}) produced a grounded
        \texttt{pin\_version} proposal for \texttt{scipy==1.13.1}, using the
        real compatibility-evidence intersection on the first attempt.
\end{itemize}

\subsection{What This Pilot Does and Does Not Show}

The pilot shows that real PyPI retrieval, real import-name mapping, and
real model proposal generation work together across RAGRepairAgent's
retrieval-to-proposal flow. It also shows that a timeout leads to a retry
and then to a safe abstention, not to a hang or an invented result. It
does not show an installed package, a modified environment, or a
re-executed notebook, because none of that happens at this step.
Validating a proposal is FixApplicator's job, covered next.

\subsection{Key Observation: Fixing One Dependency Can Reveal Another}
\label{sec:v-key-observation}

In each of the four non-synthetic repair cases, the applied fix removed the 
targeted error and execution then failed on a different problem. 
Case 3 was the controlled infrastructure-failure case and did not reach repair execution.
This happened across four repositories, two fix actions, and
packages with no shared code. It is not a defect in FixApplicator's
classification logic, which is unit-tested separately and reports a clean
\texttt{fixed} result as soon as one occurs. It is a property of the
dataset. The Docker pipeline's error classification records only the
\emph{first} import failure a notebook hits. A real research notebook can
depend on several packages that are each missing. Once the first one is
repaired, execution goes further and can reach the next one, which was
invisible until then. The conservative
\texttt{same\_as\_original\_error} check (\Cref{chap:methodology}) told
``a different, new problem'' apart from ``the fix did not work'' in every
one of these cases.

This pilot produced no completely clean \texttt{fixed} outcome, even
though it was designed to find one. A clean outcome remains achievable in
principle on a single-dependency notebook. The two-round repair mode
carries the new error of a \texttt{still\_failing} result into
reclassification and explanation and, if the error is repair-eligible,
into a second repair attempt. It was demonstrated for real on cases 1 and
2 above (\Cref{sec:v-i7}): in both, the second round triggered correctly
and then abstained rather than proposing anything ungrounded.
\Cref{sec:v-final-eval} shows that this pattern also occurs frequently 
in the full evaluation: many successful targeted repairs removed the 
original dependency error but exposed a later failure.

\section{Result Logging and Knowledge-Graph Enrichment}
\label{sec:v-i6}

\subsection{Notebook-Identity Alignment}
\label{sec:v-i6-alignment}

\begin{sloppypar}
The RML mapping in \Cref{sec:m-resultlogger-rml} links a repair attempt
to the notebook it repairs. This only works if the Docker pipeline's
\texttt{notebook\_id} and \texttt{repository\_id} identify the same
notebooks and repositories as the existing FAIR Jupyter knowledge graph.
That graph was generated from the earlier, conda-based pipeline
(\Cref{sec:pd-why-docker}), not from the Docker pipeline this thesis
builds on, so the alignment could not be assumed. It was checked
directly. All \textbf{214} rows of the classification dataset
(\Cref{sec:m-classification}) were cross-checked against the knowledge
graph's own \texttt{repositories.csv} and \texttt{notebooks.csv} source
files, comparing each row's resolved repository path and notebook
filename for an exact string match. All 214 rows matched on both
\texttt{repository\_id}$\to$\texttt{repository} and
\texttt{notebook\_id}$\to$\texttt{name}, with zero missing and zero
mismatched records.
\end{sloppypar}

Within the inspected dataset, the Docker pipeline and the FAIR Jupyter
knowledge graph therefore use the same
\texttt{repository}/\texttt{notebook} primary keys for the same
notebooks. A repair attempt can link directly to its existing notebook
resource via \texttt{notebook\_id} (\Cref{sec:m-resultlogger-identity}),
and no crosswalk table between the two pipelines is needed. This result
establishes alignment for the inspected FAIR Jupyter source dataset. It
does not extend to a knowledge-graph deployment built from a different
data snapshot.

\subsection{Executing the RML Mapping with Morph-KGC}
\label{sec:v-i6-morphkgc}

\begin{sloppypar}
The RML mapping described in \Cref{sec:m-resultlogger-rml} was also
executed, with Morph-KGC, the mapping engine the existing
\texttt{run\_fairjupyter\_kg.sh} build script uses for every other table
in the knowledge graph. A \texttt{repair\_attempts.csv} file was
assembled from the real classification, explanation, and repair-proposal
pilot records reported in \Cref{sec:v-i4}. No live fix-application batch
output existed yet, so one row used a labelled synthetic FixApplicator
record, so that the outcome and post-repair error fields could also be
exercised in the generated RDF.
\end{sloppypar}

Running the mapping over this file produced valid Turtle with no RML or
Turtle syntax error. The resulting RDF was then inspected directly. A
SQLite column left \texttt{NULL}, such as an abstained attempt's
\texttt{install\_name}, produced no triple for the corresponding
predicate, never an empty-string literal. \texttt{repr:exception} and
\texttt{repr:msg} appeared only on the one row that carried a post-repair
error. \texttt{prov:endedAtTime} was present, typed
\texttt{xsd:dateTime}, on every row.

The generated \texttt{repr:hadRepairAttempt} links were also checked
against real notebook resources rather than against the CSV's
\texttt{notebook\_id} column alone. The existing, unmodified
\texttt{notebooks.rml.ttl} was run against the real \texttt{notebooks.csv}.
It produced 627{,}127 triples, confirming that this file executes as the
rest of the knowledge graph expects. The notebook IRIs the repair mapping
links to were present there, typed \texttt{repr:Notebook} and carrying
the expected \texttt{pav:retrievedFrom} link to their repository. All
validation output was written to a scratch location; the FAIR Jupyter
knowledge-graph checkout itself was left untouched.

This pilot shows that the mapping produces syntactically valid RDF for
real data, links correctly to existing notebook resources for the
records tested, and handles missing values and the PROV-O time literal
correctly.

This pilot check used a small, real sample built for the purpose. The
same mapping was afterwards run, unchanged, over the complete
\texttt{repair\_attempts} table of the final evaluation; the next
subsection reports that run.

\section{Final Evaluation on the Reserved Evaluation Split}
\label{sec:v-final-eval}

The previous sections report results from smaller pilot runs used to validate
individual components and the integrated pipeline. This section presents the
final evaluation on the reserved evaluation split introduced in
\Cref{chap:problem-dataset}. Unlike the pilots, the complete frozen pipeline
was executed unattended across the full evaluation set using real external
services and Docker execution.

The final run completed successfully and passed all 18 post-run integrity
checks described in \Cref{sec:v-final-manifest}. The following subsections
describe the evaluation design, report the explanation and repair results, and
analyse the behaviour of the complete pipeline. A separate model-sensitivity
evaluation is presented in \Cref{sec:v-model-sensitivity}.

\subsection{Evaluation Design}
\label{sec:v-final-design}

The orchestrator was invoked with a two-round repair budget
(\texttt{max\_rounds = 2}) over all 187 evaluation rows. For every notebook, 
Round 1 classifies and explains the original failure. 
If retrieval can ground a repair proposal, the pipeline passes it to 
FixApplicator, which applies the repair and re-executes the notebook. If Round 1 reached
FixApplicator, came back \texttt{still\_failing}, and the notebook now
fails on a genuinely new error, that error is reclassified by the same
classifier used for every original row and explained as a record of its
own, whatever its scope (\Cref{sec:m-orchestrator-round2}). Round 2 is
attempted only when the reclassified error is itself pip-repair-eligible.
It runs the same RAGRepairAgent and FixApplicator components, targeting
only the newly exposed error, inside a freshly rebuilt container. That
container first reproduces Round 1's already-validated fix before Round
2's own fix is applied; \Cref{sec:m-fixapply-round2} explains why this
step is necessary. Two rounds is the hard cap; no third round exists.

Two populations therefore appear in the results below and should not be
confused. Explanation results are counted per \emph{encountered error}:
the 187 original failures, plus every newly exposed error that was
reclassified after Round 1, whether or not it was then repaired. Repair
results are counted per \emph{repair-agent invocation} and per
\emph{notebook}. A Round-2 explanation call is not a repair-agent
invocation and enters no repair metric.

As explained in \Cref{sec:orchestrator}, Round 1 and Round 2 are not two
separate experiments. Both conditions are read from the same run, so
Ollama's non-zero sampling temperature cannot turn ordinary run-to-run
variation into an apparent Round-2 effect. The comparison that follows is
between the outcome after Round 1 and the final outcome after up to two
rounds of the same execution, not between two independently sampled
runs.

Each of the 187 rows is a notebook execution already known to fail with
a dependency error before this evaluation began. Re-executing a notebook
after a repair can expose a dependency error that was not visible in the
original dataset row -- simply because execution now reaches further
into the notebook than it did before. \Cref{sec:v-final-interpretation}
returns to what this means for interpreting the results below.

\subsection{Reproducibility Manifest and Evaluation Freeze}
\label{sec:v-final-manifest}

The final evaluation was performed only after the implementation, prompts,
package mapping, and evaluation split had been frozen. A machine-readable
evaluation manifest records the source revision, model configuration, evaluation
split, and SHA-256 hashes of the files that define the pipeline. This makes it
possible to trace the reported results back to the exact configuration used to
produce them.

Both final model runs used the same frozen pipeline implementation and the same
187 evaluation records. They were executed from the same implementation commit
(\texttt{46d90aa4}) with identical pipeline-component hashes. The runs differ only
in the language model and the model- and provider-specific serving configuration
described in \Cref{sec:v-model-sensitivity}.

\paragraph{Repository revision during re-execution.}
One limitation affects how the re-execution results should be interpreted.
FixApplicator supports checking out the repository commit recorded by the upstream
pipeline (\Cref{sec:m-fixapply}). During the final evaluation, however, the
metadata database configured for FixApplicator could not be accessed from the WSL
environment because its configuration contained a Windows-style path. The commit
lookup therefore returned no commit, and the evaluated repositories were cloned
from their current default branches instead.

Of the 73 real FixApplicator attempts, 71 record that commit checkout was skipped;
the remaining two failed during cloning before a checkout could be attempted. The
same metadata lookup also provides the locations of repository
\texttt{setup.py} files. Because this metadata was unavailable, those files were not
installed during the final runs. Root-level \texttt{requirements.txt} files were still
used where available (\Cref{sec:m-fixapply-docker}).

The final evaluation should therefore not be interpreted as a commit-pinned
reproduction of the historical executions. A repository may have changed between
the original failure and the evaluation run. This limitation applied equally to both
model runs, so their comparison in \Cref{sec:v-model-sensitivity} uses the same
execution policy.

The raw results are kept separate from the derived evaluation metrics. Each run
produces a per-notebook JSONL trace and a \texttt{repair\_attempts} SQLite database
(\Cref{subsec:repair-table}). The evaluation tables and summary metrics are computed
from these raw outputs rather than from manually adjusted intermediate values. The
same SQLite database is also used for the full knowledge-graph materialisation
reported in \Cref{sec:v-i6-fullscale}.

Before any metrics are reported, the raw output is checked by 18 integrity tests.
These checks verify the expected notebook population, the Round-1 and Round-2
structure, shared run identifiers, the relationship between newly exposed errors and
their Round-2 records, and consistency with the frozen configuration. Both final
evaluation runs passed all 18 checks. \Cref{fig:v-provenance} summarises this
evaluation chain.

\subsection{Explanation Completion and Schema Validity}
\label{sec:v-final-explanation}

LLMExplainer is measured before the repair results, in the order the
pipeline runs, with two separate questions that are easy to conflate.
The first is \emph{completion}: did the explanation call return a response
that could be processed at all, within the one-retry budget? A call that
timed out at the explainer's 120-second limit, or that met an unavailable
model service, produced no model output to judge. Such a record is a
\emph{runtime failure}, attributed to the model service and the machine it
ran on, not to the model's output. The second question is \emph{schema
validity among completed responses}: of the responses that did arrive, how
many validated against the six-field explanation schema
(\Cref{sec:m-explanation-deviation})? Only this second figure says
anything about the quality of what the model produced. A single combined
``validity'' number would let a slow machine look like a model that writes
malformed JSON, so the two are kept apart throughout.

Both are counted per encountered error, one record each. Retries are
attempts, not records: a record that needed the corrective second attempt
counts once, and the attempt counts appear separately.
\Cref{tab:v-final-explanation} gives the Gemma-2 9B results for three
populations: the 187 original failures, the newly exposed errors
reclassified after Round 1, and the two combined.

of the evaluation machine and the model's speed on it, not of the model's
output. Third, the Round-2 population is complete. Round 1 exposed and
reclassified 50 new errors: 48 \texttt{missing\_package}, one
\texttt{system\_library}, and one non-dependency \texttt{IndexError}
classified \texttt{out\_of\_scope}. All 50 received an explanation on the

50 is a count of explained records, not of repairable ones.

Schema validity is a structural check and nothing more. Whether these
explanations are understandable, detailed enough, and perceived as correct
by a reader is the question the human evaluation in \Cref{sec:v-human-eval}
answers, for the original-failure explanations only.

\subsection{Primary Repair Results}
\label{sec:v-final-primary}

Full notebook recovery means a notebook re-executes from beginning to
end with no error. No evaluation notebook achieved this, in either
round: Round-1 repair success is 0/187, the final success rate after up
to two rounds is 0/187, and Round 2 therefore added no fully fixed
notebook. Full recovery is the answer to RQ2's second half. Its first
half, whether the targeted dependency error was removed, is a different
question with a different denominator, and \Cref{sec:v-final-targeted}
answers it at the level of individual repair attempts.

\subsection{Targeted Dependency-Error Resolution}
\label{sec:v-final-targeted}

Full notebook recovery requires every dependency problem in a notebook
to be gone after re-execution. A narrower, attempt-level question asks
whether the one dependency error that a repair attempt targeted was
removed, regardless of whether the notebook then failed on something
else. A repair attempt counts as resolving its targeted error in two
cases: the notebook becomes \texttt{fixed}, or it stays
\texttt{still\_failing} but the original error is gone and the
conservative \texttt{same\_as\_original\_error} check
(\Cref{chap:methodology}) confirms that the notebook moved on to a
genuinely different error.

Across the 73 real FixApplicator attempts in this evaluation (61 in
Round 1, 12 in Round 2), 62 resolved the error they targeted: 50 of the 61
Round-1 attempts and all 12 Round-2 attempts. The targeted
dependency-error resolution rate is therefore 84.9\% (62/73). This is an
attempt-level figure, not a notebook-level one, and it should not be
confused with the 0\% full-recovery figure above;
\Cref{fig:v-final-funnel} (\Cref{sec:v-final-breakdown}) shows both levels
side by side. No notebook completed successfully within two rounds, but
the large majority of individual repair attempts removed the specific
dependency error they addressed. Re-execution then frequently exposed a
following failure. This is the pattern observed at pilot scale in
\Cref{sec:v-key-observation} and traced through one real record in
\Cref{sec:m-worked-example}.

\subsection{Abstention: Round 1, Round 2, and Final State}
\label{sec:v-final-abstention}

In a large share of its invocations, RAGRepairAgent declined to propose a
repair, so no repair attempt followed. This is abstention. It is
distinct from an infrastructure fault and from a failed repair: when the
system lacks grounded package information, it refuses to generate an
unsupported fix rather than guessing.

\begin{sloppypar}
In Round 1, RAGRepairAgent abstained on 126 of the 187 rows (67.4\%, the
Round-1 abstention rate). All 126 cases have the same cause: PyPI
retrieval returned \texttt{mapping\_unknown}, meaning that
RAGRepairAgent's static import-to-distribution mapping
(\Cref{chap:methodology}) could not resolve the failing import to a
supported PyPI package. In all 126 cases the language model was never
called; the abstention happens one layer earlier, at retrieval.
\end{sloppypar}

Round 2 does not simply repeat this figure. Of the 187 rows, 50 had a
real Round-1 attempt that came back \texttt{still\_failing} on a genuinely
new error. All 50 were reclassified and explained
(\Cref{sec:v-final-explanation}). The 48 newly exposed
\texttt{missing\_package} errors were repair-eligible; the two others, a
missing system library and a non-dependency \texttt{IndexError}, fell
outside repair scope and received no second round.
Table~\ref{tab:v-final-round2} shows what happened to the 48 eligible
notebooks. Only 12 received a second repair proposal and a real second
FixApplicator attempt. The remaining 36 abstained again. As in Round 1,
every one of these 36 abstentions is a \texttt{mapping\_unknown} case:
the newly exposed error's import name had no entry in the package mapping
either.

separate figures because they answer different questions. The first asks
how often the very first repair attempt could not get past package
resolution. The second asks how often the notebook's terminal repair
decision was an abstention: 126 notebooks stopped at Round 1 without any
proposal, while 36 received a Round-1 proposal and repair, exposed a new
error, and then abstained on that newly exposed error in Round 2. All 162
final-state abstentions, in both rounds, have the same underlying cause:
\texttt{mapping\_unknown}. The dominant reason a repair attempt did not
happen, in whichever round, is therefore package-mapping coverage, not
the language model or the grounding logic.

\subsection{Proposal Quality and Proposal Coverage}
\label{sec:v-final-proposal}

RAGRepairAgent was invoked 235 times across both rounds (187 in Round 1,
48 in Round 2). Of those invocations, 73 reached the point of calling the
language model. The remaining 162 abstained beforehand, for the
\texttt{mapping\_unknown} reason described above. All 73 responses the
model produced passed schema validation, and all 73 also passed grounding
validation against the retrieved PyPI evidence. Whenever RAGRepairAgent's
retrieval step supplied a resolved candidate distribution, the model's
proposal was therefore schema-valid and grounded. This gives a proposal
validity rate of 100\% (73/73), a grounding pass rate of 100\% (73/73
schema-valid proposals), and a grounded proposal rate among LLM
invocations of 100\% (73/73).

These three figures are conditional on the language model having been
called. They say nothing about overall proposal coverage. Counting all
235 repair-agent invocations, including the 162 that abstained before
reaching the model, only 73 ended in a grounded proposal: an overall
grounded proposal coverage rate of 31.1\% (73/235). The contrast between
these two figures is central to interpreting this system. Its output is 
schema-valid and grounded whenever it produces a proposal. But the static package-mapping
coverage decides whether the model is called at all, and it is the
binding constraint on how often the model gets that chance.

\subsection{Infrastructure Failures}
\label{sec:v-final-infra}

Two of the 187 evaluation rows (1.1\%) ended in an infrastructure
failure: an environment or tooling fault, unrelated to repair quality,
that prevented a fair trial of the method (\Cref{chap:methodology}).
These cases are reported separately from abstentions, method failures, and
\texttt{still\_failing} outcomes, so that their external cause remains visible. 
They nevertheless remain in the 73-attempt denominator used for targeted-error resolution.
This follows the same infrastructure-versus-method
distinction already used throughout the pilots earlier in this chapter.

The rule behind this distinction is conservative. A case is classified as
an infrastructure failure only when there is concrete evidence of an
external execution or environment problem: a clone failure, a Docker
build failure, a timeout, or a similar tooling fault. When the cause of a
failure is ambiguous, it is kept as a method failure. Otherwise an
ambiguous case could be absorbed into ``infrastructure'' and excluded
from the method's own results, which would make the reported repair
figures look better than what was observed.

repair was attempted because the two-round budget had been exhausted.

This case illustrates why targeted-error resolution and full notebook recovery are
reported separately. At the repair-attempt level, both attempted fixes succeeded
in removing the errors they targeted. At the notebook level, the final outcome
remains \texttt{still\_failing} because another dependency error remained after
Round~2. A single binary success measure would not capture this distinction.

\subsection{Manual Validation of PyPI Distribution Resolution}
\label{sec:v-final-pypi}

A separate, small diagnostic sample of 20 import names was manually
checked against the real PyPI registry. It covers every name already
present in the package mapping, plus the most frequently exercised
names that are not. Of the 20, 17 were names a human reviewer could
confidently resolve to one specific distribution, or confirm as
unresolvable. The remaining 3 were left unresolved on purpose, because
no single correct distribution could be determined by hand either.
Against those 17 manually resolvable cases, RAGRepairAgent's retrieval
step resolved the correct distribution in 7 (41.2\%).

This is a small diagnostic sample, not a population-wide measurement of
package-resolution accuracy. It is, however, consistent with the
abstention results in \Cref{sec:v-final-abstention}. A package mapping
that resolves fewer than half of a manually checked diagnostic sample of
import names has the kind of coverage gap that would be expected to
produce a high \texttt{mapping\_unknown} abstention rate at full
evaluation scale, which is what was observed. The two pieces of evidence
are consistent with each other; this does not prove that one caused the
other.

\begin{sloppypar}
Table~\ref{tab:pd-top-modules} gives concrete cases of this gap.
\texttt{rpy2} (15 occurrences), \texttt{cana} (12), \texttt{celloracle} (12),
\texttt{keras} (7), and \texttt{statsmodels} (4) are all frequent failing
modules in the working dataset, and none of the five has an entry in
\texttt{config/}\allowbreak\texttt{package\_mapping.yaml}
(\Cref{sec:m-repair-retrieval}). Every one of them therefore resolves to
\texttt{mapping\_unknown} at retrieval time, even where the correct PyPI
distribution shares the import's own name. Some of the five might resolve
correctly if attempted, but the mapping table was never told about them,
so RAGRepairAgent abstains before finding out.
\end{sloppypar}

The mapping table was not extended to cover these five names, or any other
name surfaced by the final evaluation, once this pattern became visible.
Extending it would have changed a repair-eligibility rule in direct
response to the reserved evaluation split's own outcome, which is exactly
the kind of tuning this evaluation is designed to avoid
(\Cref{sec:v-final-manifest}). The limitation is also not specific to the
size of this particular table. Any manually curated mapping needs
continued maintenance to track newly published or renamed packages, and
it cannot resolve an import name it has never been told about, whatever
its starting size. This is the same structural limitation already
identified in the static knowledge-graph approaches this thesis positions
itself against (\Cref{sec:rw-restoring}).

\subsection{What Limits Full Recovery}
\label{sec:v-final-interpretation}

The results above separate three populations. Every proposal the language
model produced was schema-valid and grounded (73 of 73). Most real repair
attempts removed the error they targeted (62 of 73,
\Cref{sec:v-final-targeted}). No notebook ran end to end (0 of 187,
\Cref{sec:v-final-primary}). Two factors, one acting before the model's
decision and one after it, explain the gap between the last two.

The first is package-mapping coverage, a deliberate system behaviour.
Retrieval resolved the failing import for 73 of 235 repair-agent
invocations and abstained on the other 162 rather than guess an
unsupported package name (\Cref{sec:v-final-abstention}). The second is a
property of the notebooks themselves. Many repaired notebooks exposed
further dependency errors in sequence, so removing one error frequently
exposed the next (\Cref{sec:v-key-observation}), and the two-round cap
determines how far along such a chain the system can follow. The results
do not show how
many errors any notebook has in total, only that two rounds did not reach
the end of the chain for any of them.

\subsection{LLM Model Sensitivity Analysis}
\label{sec:v-model-sensitivity}

The final evaluation above uses one specific open model, Gemma-2 9B,
served locally through Ollama. A natural question follows: how much of
the reported behaviour comes from that specific model, and how much from
the pipeline around it? This is RQ3. To answer it, the same repair layer
was run over the same 187 evaluation notebooks with the language model
replaced. Everything else was held fixed: the pipeline structure, the
prompts and few-shot examples, the JSON schemas, the classifier, PyPI
retrieval and the package mapping, grounding validation, FixApplicator,
the Round-2 trigger and explanation logic, the evaluation records, and
the repair policy. Both runs record the same Git commit and byte-identical
component hashes in their manifests (\Cref{sec:v-final-manifest}). Only
model- and provider-specific serving settings differed: the model name,
the provider (local Ollama against a remote endpoint), and the calibrated
Qwen output-token budget described next. The comparison is therefore
controlled at the level of the pipeline; not every configuration field
was identical.

\textbf{Setup.} The replacement model is Qwen3.6-35B-A3B-MLX-8bit, served 
through a remote OpenAI-compatible endpoint using Kiste. A small
provider abstraction lets the pipeline call either backend through the
same interface; Gemma's own configuration and code path are untouched.
Qwen needed one setting change: a larger completion budget. At Gemma's
setting of 700 tokens, Qwen's responses were often cut off before they
finished. A calibration run over five development-split notebooks, never
part of the evaluation split, tested budgets of 1400, 2800, and 4096
tokens. Truncation still occurred at 1400 and once at 2800, but not at
4096. The budget of 4096 was therefore the smallest of the three tested
values that eliminated observed truncation; smaller untested budgets might
also have worked.
The Qwen run is identified as
\texttt{i11-eval-qwen-round2-explanations-20260919T131359Z}. It processed
all 187 records and passed all 18 integrity checks.

outcome, the newly exposed error, the Round-2 decision, the Round-2
proposal and outcome, and the final classification. The remaining 13
notebooks differ in exactly one field: the version chosen in the Round-1
\texttt{pin\_version} proposal. These are execution ids 189 to 201, all
\texttt{wrong\_version} failures on
\texttt{numpy.VisibleDeprecationWarning} from two repositories of the same
group. Gemma chose \texttt{numpy==1.26.3} in all 13; Qwen chose
\texttt{numpy==1.26.4} in all 13. The retrieval evidence given to both
models was identical: the same five candidate versions, including both
1.26.3 and 1.26.4, and the same compatibility constraint \texttt{<2.0.0}
from the curated registry (\Cref{tab:m-compat}). Both choices are valid,
grounded candidates within that constraint. This is therefore a genuine
model-selection difference, not a retrieval or pipeline difference: given
the same evidence, Gemma preferred the second newest compatible release
and Qwen the newest.

The difference stopped there. In all 13 notebooks the pin installed
successfully under both models, and re-execution then exposed the same
new error (\texttt{No module named 'cxsystem2'} or \texttt{'matplotlib'},
depending on the repository). The Round-2 reclassification, explanation,
eligibility decision, proposal, and outcome were identical; the targeted
Round-1 error counted as resolved in both; and the final classification
was the same. Model choice produced a small difference in version
selection for 13 NumPy repairs, but this did not change any measured
downstream repair outcome in the evaluation set.

\textbf{Interpretation.} Replacing Gemma-2 9B with Qwen3.6-35B-A3B-MLX-8bit did not change any
aggregate repair result. The models made a different repair decision for 13
of the 187 notebooks, but these differences affected only which compatible
NumPy version was selected. They did not change any downstream execution
outcome.

This result reflects the role of the deterministic retrieval and grounding
layers. The model can choose only from package versions that were retrieved
from PyPI and passed the applicable compatibility constraints. More than one
version can satisfy these constraints, which is where the two models differed
in this evaluation.

The two runs also had the same Round-1 abstention count of 126 out of 187.
These abstentions occurred before the repair model was called because the
package mapping could not resolve the failing import. Both models also resolved
the targeted dependency error in 62 of the 73 FixApplicator attempts, while
neither produced a fully recovered notebook within the two-round budget.

For these two model configurations, the main limits on repair coverage were
therefore package-mapping coverage and notebooks that exposed further dependency
errors after a repair. The results do not establish that one model is generally
better than the other. Qwen completed all explanation calls, whereas the Gemma
run had 27 runtime failures, but the models were served through different
environments and with different provider-specific settings. This difference
therefore cannot be attributed to the language model alone.

\section{Human Evaluation of Explanation Quality}
\label{sec:v-human-eval}

\Cref{sec:v-final-explanation} showed that every explanation Gemma-2 9B
completed was schema-valid. Schema validity is a structural check. It
does not show whether an explanation is understandable, detailed enough,
or useful to a reader, which is what objective~O1 and the plain-language
requirement NFR2 (\Cref{subsec:llmexplainer}) ask for. Only a human
reader can judge that. This section therefore reports a small human study
of perceived explanation quality.

The study rated a frozen set of 12 Gemma-2 9B explanations of
\emph{original} failures from the evaluation split. It is separate from
the automated completion and schema-validity measurements of
\Cref{sec:v-final-explanation}, and it did not rate any Round-2
explanation of a newly exposed error or any Qwen explanation. The design
was fixed, and the survey administered, before any response was analysed.

\subsection{Questionnaire}
\label{sec:v-human-eval-instrument}

The questionnaire adapts the Explanation Satisfaction Scale of Hoffman et
al.~\cite{hoffman2023measures}, a seven-item Likert scale that records a
user's own judgment of an explanation after reading it. Six of the seven
items are kept, each adapted only in its domain reference; for example,
``From the explanation, I know how the [tool] works'' becomes ``From this
explanation, I understand why the notebook failed.'' The adapted items
are listed in \Cref{tab:v-human-eval-results}. The seventh original
item, whether the explanation ``tells me how to use'' the system, is
excluded: LLMExplainer does not suggest what to do about a failure,
because deriving a repair is RAGRepairAgent's separate responsibility
(\Cref{sec:m-explanation-role}).

The item closest to the original scale's accuracy question, ``This
explanation seems correct, based on the error shown'' (Q6), is reported
throughout as \emph{perceived correctness}. It records how correct the
explanation appears to the reader, not whether it matches the notebook's
true root cause. The study does not measure objective correctness.

All six items use the same 1--5 scale (1 = strongly disagree, 2 =
disagree, 3 = neither agree nor disagree, 4 = agree, 5 = strongly agree)
after every example. The scale fits this thesis because it measures a
reader's experience of a single, static, plain-language explanation. The
System Causability Scale of Holzinger et al.~\cite{holzinger2020scs} was
not adopted, because its items assume an interactive, expert-facing
explanation interface.

\subsection{Study Design and Participants}
\label{sec:v-human-eval-pool}

\paragraph{Example pool.} Twelve explanations were drawn from the frozen
187-row evaluation split. None come from the 13-row development split
(\Cref{sec:m-explanation-example}). Five evaluation-split records had
previously been used for explanation-only smoke checking of the
implemented explainer, after the prompt-design sample had been fixed and
the design-time prompt checks had been carried out on the development
split alone (\Cref{sec:pd-i1}); that check ran under the same explanation
prompt version as the final evaluation records, and all five returned
schema-valid output on the first attempt. Because they had nevertheless
been inspected during development, they were conservatively excluded from
the human-study sampling pool. Two further
\texttt{missing\_package} records were unavailable for sampling because
their explanation call timed out in the run the pool was drawn from, so
no schema-valid explanation existed to show a participant. The eligible
sampling population is therefore 180 of the 187 evaluation records --
162 \texttt{missing\_package} and 18 \texttt{wrong\_version}, all seven
excluded records being \texttt{missing\_package} ones. All twelve
examples were generated with Gemma-2 9B under the final explainer prompt,
schema, and configuration, and the pool was frozen before any participant
response was collected. Sampling was stratified by subtype, with the
number of examples per subtype bounded by how many distinct error
signatures the eligible population contains, and it did not consult
repair outcomes or any other evaluation result. The eligible
\texttt{wrong\_version} population has only three distinct (failing
module, error message) signatures across its 18 rows, most of which share
one of two repeated NumPy or SciPy messages; all three signatures are
included once. The remaining nine positions come from
\texttt{missing\_package}, which offers 41 distinct failing modules
across 162 eligible rows, and each of the nine has a different failing
module. The pool therefore holds \textbf{9 \texttt{missing\_package} and
3 \texttt{wrong\_version}} explanations, not a balanced 6/6 split.

\paragraph{Assignment.} Each participant rated 6 of the 12 explanations.
The 12 were arranged into four fixed survey variants so that every
explanation appears in exactly two variants, which balances exposure
without a shared anchor example. Participants were assigned to variants
in round-robin order as they were recruited, and the order of the six
explanations within a variant was randomised.

\paragraph{Procedure.} For each explanation, a participant saw only the
original error type and message together with the explanation's
\texttt{summary}, \texttt{root\_cause}, \texttt{evidence}, and
\texttt{limitations} fields, rendered as plain text and unedited. The
repository name, the source code, the model's
\texttt{explanation\_confidence}, and every outcome of the final
evaluation, such as whether the notebook was repaired or whether a
Round-2 attempt fired, were withheld, because they could bias the
judgment of the explanation itself. The same six items followed every
explanation in the same order. Two optional free-text questions at the
end asked what was unclear or missing and what would make the
explanations more helpful; these are supplementary feedback, not part of
the scale.

\paragraph{Participants.} The only requirement was general programming
experience. Familiarity with Python or Jupyter was not required, and no
machine-learning expertise was needed, because the explanations are
written for exactly this audience (NFR2). A short, anonymous background
section recorded self-reported programming experience, Python and
Jupyter familiarity, and prior experience with package errors. The
target was a convenience sample of 15--20 participants, sized for a
descriptive study.

The survey ran as four LimeSurvey instances, one per variant, between
2026-09-15 and 2026-09-17, and produced 18 raw responses. Three were
excluded before analysis: one respondent declined consent, and two left
after the consent page with no rating filled in. The remaining
\textbf{15 responses are complete}, with all 36 rating cells (6
explanations $\times$ 6 items) filled in; variants A--D contributed 3,
4, 4, and 4 complete participants. This gives \textbf{90 explanation
evaluations} and \textbf{540 individual ratings}. Of the 15 participants,
10 described their programming experience as intermediate, 4 as advanced
or professional, and 1 as beginner. Seven use Python regularly, seven
had used it a little, and one had never used it. Eleven had used Jupyter
Notebooks a few times, three never, and one regularly. All had
encountered a missing-package or package-version error, 11 occasionally
and 4 frequently.

\subsection{Analysis and Limitations}
\label{sec:v-human-eval-analysis}
\label{sec:v-human-eval-limitations}

For each of the six items, the analysis reports the number of ratings,
the median, the interquartile range (IQR), the full 1--5 frequency
distribution, and the percentage of ratings of 4 or 5 (\%4--5). These
statistics are computed overall, by subtype, and per explanation,
exactly as planned before any response was collected. No inferential
test is computed. Every statistic is produced by one analysis script
directly from the raw survey exports, using functions that were written
and unit-tested while the study was being designed.

Cronbach's alpha is reported as a supplementary internal-consistency
statistic only. It describes whether the six items move together in the
collected data. It is not a measure of agreement between participants,
it does not show that the six items measure a single construct, and it
is not used to combine the items into one composite score. Item-level
results remain the primary output.

Five limitations bound what the results can show. First, the study is a
convenience sample of 15 participants, each rating 6 of 12 explanations.
The 90 evaluations are clustered within 15 people, not 90 independent
judgments, and the results describe this group and this pool, not
programmers or explanations in general. Second, participants judged a
rendered error message and explanation, not the original notebook and
its code. Third, the ratings measure perceived quality; Q6 in
particular records whether an explanation struck a reader as correct,
not whether it matches the notebook's true root cause. Fourth, no
baseline or alternative explanation was shown, so the results describe
this component in isolation. Fifth, the subtype comparison rests on 9
distinct \texttt{missing\_package} explanations against 3 distinct
\texttt{wrong\_version} explanations, with 67 and 23 evaluations
respectively, and is descriptive only. In addition, the study covers
original-failure Gemma-2 9B explanations alone. The 50 Round-2
explanations and the 237 Qwen explanations of
\Cref{sec:v-final-explanation,sec:v-model-sensitivity} were evaluated
automatically for completion and schema validity only, and no participant
rated any of them. The broader
threats to validity are collected in \Cref{sec:v-threats}.

\paragraph{Qualitative feedback.} Five of the 15 participants answered at
least one of the two free-text questions, giving six answers in total.
Two themes recur. Several comments were unqualified positive assessments,
such as ``Nothing. Everything is clear'' and that the explanations ``were
very helpful and also provide enough information on understanding exactly
what is working wrong.'' Several others asked for more causal or
technical detail: one participant asked for ``more detailed explanation
about the error message'', and another wrote that some explanations
``repeated the error message and could have explained the cause a little
more'' and suggested adding ``specific details, such as the correct
package name or what kind of version incompatibility might be
involved.'' No broader thematic analysis is claimed from six comments.

\paragraph{Interpretation.} Within the scope of this study, the results
answer the reader-facing half of RQ1 positively. Participants, whose
self-reported Python and Jupyter experience ranged from none to regular
use, rated the explanations positively on every item. Understanding (Q1)
scored highest at 92.2\%, followed by detail and completeness (Q3 and Q4,
91.1\%), usefulness (Q5, 87.8\%), and perceived correctness (Q6, 86.7\%).
Satisfaction (Q2) was the weakest item at 84.4\%. It is still clearly
positive, but it is the item to which the free-text requests for more
causal, package, and version detail most plausibly apply. The spread
across items is about eight percentage points, so this ordering describes
emphasis within a generally positive set of ratings rather than a sharp
separation. The limitations of \Cref{sec:v-human-eval-limitations}
apply: the ratings are perceived quality from a 15-participant
convenience sample, with no alternative explanation method for
comparison. Within those limits, the plain-language explanations
LLMExplainer produced were understandable, useful, and perceived as
correct by the readers in this study, with satisfaction the weakest item
and the one the free-text feedback pointed at.

\section{Threats to Validity}
\label{sec:v-threats}

This section collects the limitations that affect how the evaluation as a
whole should be read. Each point is stated once, with a reference to the
section that discusses it in full.

\subsection{Internal Validity}
\label{sec:v-threats-internal}

\begin{itemize}
  \item \textbf{LLM sampling is not deterministic.} Both models run at a
    non-zero temperature
    (\Cref{sec:m-repair-retrieval,sec:v-model-sensitivity}), so a repeated
    prompt need not reproduce the same output. The Round-1-versus-Round-2
    comparison reads both conditions from one run, so sampling variation
    cannot appear as a Round-2 effect (\Cref{sec:v-final-design}). Each
    model's run in the Gemma/Qwen comparison is likewise a single run.
  \item \textbf{The two models were served differently.} Gemma ran on
    local, CPU-only Ollama; Qwen ran on a remote OpenAI-compatible endpoint
    with a larger output-token budget (\Cref{sec:v-model-sensitivity}).
    Serving hardware, latency, and queuing are therefore confounded with
    model choice. Gemma's 27 explanation runtime failures against Qwen's
    none are reported as a property of the serving setup, not as a
    model-quality difference. The 13 notebooks with a different Round-1
    version choice are the opposite case: the retrieval evidence was
    identical, so that difference is attributed to the models.
  \item \textbf{Repositories were not commit-pinned.} FixApplicator could
    not reach its configured metadata database in the final evaluation
    environment, so every repository was cloned from its current default
    branch rather than checked out at the originally failing commit
    (\Cref{sec:v-final-manifest}). A repository changed by its authors in
    the meantime could behave differently on re-execution. The same
    fallback policy applied to both model runs, which reduces this threat
    to the model comparison, although a repository could in principle have
    changed between the two run dates. The absolute repair figures describe
    the repositories as they were on the run dates.
  \item \textbf{Infrastructure failures are kept apart from repair-method
    failures.} A clone, build, or container failure
    (\Cref{sec:m-fixapply-docker}) is recorded as \texttt{apply\_error} and
    counted as an infrastructure failure only when there is concrete
    evidence of an external fault; an ambiguous case stays a method failure
    (\Cref{sec:v-final-infra}). Infrastructure failures are labelled
    separately from method failures so that their external cause remains
    visible. They nevertheless remain unresolved cases in the 73-attempt
    targeted-resolution denominator, so this classification does not
    inflate the reported 62/73 resolution rate.
  \item \textbf{The evaluation split was reserved and the configuration
    frozen.} The 187-row split was reserved at dataset-preparation time
    (\Cref{sec:pd-i1}). No prompt, mapping entry, or repair rule was
    designed against it, and the package mapping was not extended after
    the abstention pattern became visible (\Cref{sec:v-final-pypi}). Both
    final runs executed from one recorded commit under a hash-checked
    configuration (\Cref{sec:v-final-manifest}).
\end{itemize}

\subsection{Construct Validity}
\label{sec:v-threats-construct}

RQ2 asks whether the targeted dependency error is resolved and whether
the notebook recovers; RQ1 asks whether the explanations are
understandable to a reader. The metrics of this chapter measure these
concepts with the following qualifications.

\begin{itemize}
  \item \textbf{Targeted-error resolution is not full notebook recovery.}
    An attempt can remove exactly the dependency error it targeted and
    still leave the notebook failing on another
    (\Cref{sec:v-final-targeted,sec:v-case-study}). The two figures are
    therefore reported side by side, together with proposal validity and
    grounding validity, rather than combined into one success score
    (\Cref{fig:v-final-funnel}); a single score would hide the gap on which
    the central finding depends.
  \item \textbf{A schema-valid, grounded proposal is not necessarily a
    correct repair.} Schema and grounding validity
    (\Cref{sec:v-final-proposal}) show only that the model's output has the
    right shape and cites evidence RAGRepairAgent retrieved. Whether the
    fix works is decided by FixApplicator's re-execution alone.
  \item \textbf{Explanation completion and schema validity are runtime and
    structural measures.} A timed-out explanation call is a runtime failure
    with no output to judge, not a malformed response, and the two are kept
    apart (\Cref{sec:v-final-explanation}). Schema validity of a completed
    response says nothing about whether a reader finds it understandable
    or useful, which is what O1 and NFR2 ask for.
  \item \textbf{The human evaluation measures perceived quality.} It
    answers the reader-facing question for a frozen pool of Gemma
    original-failure explanations (\Cref{sec:v-human-eval}). Its
    correctness item records whether an explanation struck a reader as
    correct, not whether it matches the true root cause
    (\Cref{sec:v-human-eval-limitations}).
\end{itemize}

\subsection{External Validity}
\label{sec:v-threats-external}

\begin{itemize}
\begin{sloppypar}
  \item \textbf{One dataset, one failure class.} Every record comes from
    the Docker-based FAIR Jupyter pipeline over PubMed-Central-linked
    notebooks (\Cref{sec:pd-why-docker}), and only
    \texttt{ModuleNotFoundError} and \texttt{ImportError} failures are
    considered (\Cref{sec:pd-source}). The results say nothing about other
    notebook collections or about logic or data errors.
  \item \textbf{Repair is pip/PyPI-based.} Every automated fix is a
    \texttt{pip install} or a version pin for a \texttt{missing\_package}
    or \texttt{wrong\_version} failure (\Cref{sec:pd-scope}).
    \texttt{system\_library} failures, which need system-level
    installation, are outside repair scope by design (\Cref{fig:pd-scope}),
    and an import the package mapping cannot resolve is abstained on rather
    than repaired (\Cref{sec:v-final-abstention}). Nothing here shows how
    the approach would fare in a Conda-managed environment or another
    package ecosystem.
  \item \textbf{Two open LLM configurations were evaluated.} Gemma-2 9B and
    Qwen3.6-35B-A3B-MLX-8bit are the only models run through the full
    evaluation (\Cref{sec:v-model-sensitivity}). Their agreement describes
    these two models under this grounded design; other open or proprietary
    models could behave differently.
  \item \textbf{The human study is small and narrow in scope.} It is a
    convenience sample of 15 participants whose Python and Jupyter
    experience ranged from none to regular use
    (\Cref{sec:v-human-eval-results}), and it rated only the frozen pool of
    Gemma original-failure explanations, not Round-2 or Qwen explanations
    (\Cref{sec:v-human-eval-limitations}). Its ratings describe how this
    group judged this pool, not how programmers in general would.
\end{sloppypar}
\end{itemize}

\subsection{Conclusion Validity}
\label{sec:v-threats-conclusion}

\begin{itemize}
  \item \textbf{Denominators are small.} The evaluation split has 187
    notebooks, and only 73 of the 235 repair-agent invocations reached the
    language model and FixApplicator (\Cref{sec:v-final-abstention}). Every
    proposal-quality and targeted-resolution figure is therefore a
    proportion over 73 attempts, and subgroup figures such as the 12
    Round-2 attempts or the 18 \texttt{wrong\_version} rows rest on even
    fewer cases. A different 187-row sample could give different exact
    percentages.
  \item \textbf{The Gemma/Qwen comparison is descriptive.} It compares two
    single runs of the same 187 notebooks (\Cref{sec:v-model-sensitivity})
    without a significance test. The identical aggregates are consistent
    with the grounding layer strongly constraining the available repair
    choices, but they are not evidence that either model is generally
    better, and the two need not agree where a candidate set leaves more
    choice.
  \item \textbf{The two-round cap bounds conclusions about longer repair
    chains.} \Cref{sec:v-case-study} shows a notebook that exposed a third
    dependency error after two successful targeted repairs. The evaluation
    shows that two rounds were not enough for such notebooks; it cannot
    say what a third round would have found, or whether further errors
    lay behind the third (\Cref{sec:m-fixapply-round2}).
  \item \textbf{The human-study statistics are descriptive.} The 90
    explanation evaluations come from 15 participants who each rated 6 of
    12 examples, so the per-item percentages and Cronbach's alpha are
    computed over ratings clustered within 15 people, not 90 independent
    raters. The subtype comparison rests on 9 and 3 distinct examples
    (\Cref{sec:v-human-eval-pool}), and no inferential claim is made.
\end{itemize}

None of these points overturns the results reported in this chapter. They
mark the boundary of what the results can claim, so that
\Cref{chap:conclusion} states no more than this evaluation supports.

\section{Chapter Summary}
\label{sec:v-summary}

This chapter reported several kinds of evidence, in increasing order of
scale. The automated test suite (\Cref{sec:v-testing}, 711 tests) shows
that every implemented component behaves as designed against controlled,
mocked inputs. The component-by-component pilots
(\Cref{sec:v-i4,sec:v-i5,sec:v-i6}) and the small orchestrator pilot
(\Cref{sec:v-i7}) showed that each component, and the orchestrator that
connects them, also behaves correctly against its real external system: a
real Ollama model, the live PyPI registry, real Docker execution, real
GitHub repositories, and the real Morph-KGC mapping engine. These pilots
surfaced concrete problems that only a real pilot could have found: a
timeout set too low, two missing package mappings, and three
environment-specific bugs.

\Cref{sec:v-final-eval} then reported the final evaluation: the final
frozen implementation, run with Gemma-2 9B over the 187-row evaluation
split with a two-round budget. For RQ1, Gemma completed 160 of the 187
original-failure explanations and all 50 explanations of newly exposed
Round-2 errors; every one of the 210 completed responses was schema-valid,
and the 27 missing records were timeouts and one service error of the local
model service. The human study (\Cref{sec:v-human-eval}) adds the reader's
view for the original-failure explanations: 15 participants, 540 ratings,
88.9\% Agree or Strongly Agree, every item with a majority-agree median.
For RQ2, the two levels of the repair result stay apart: 62 of the 73 real
repair attempts (84.9\%) removed the error they targeted, while 0 of 187
notebooks ran end to end. Every one of the 73 proposals the model produced
was schema-valid and grounded, but only 73 of 235 repair-agent invocations
reached the model at all, because a \texttt{mapping\_unknown}
package-resolution gap accounted for all 162 abstentions. Many repaired
notebooks also exposed further dependency errors in sequence, and the
two-round cap does not follow such a chain to its end
(\Cref{sec:v-final-interpretation,sec:v-case-study}). Two rows ended in
an infrastructure failure and one in a method failure; these categories
are reported separately in the final-outcome breakdown, while the
infrastructure cases remain unresolved in the 73-attempt
targeted-resolution denominator.

For RQ3, \Cref{sec:v-model-sensitivity} repeated the evaluation with
Qwen3.6-35B-A3B-MLX-8bit in place of Gemma-2 9B, with the pipeline held
fixed and only model- and provider-specific serving settings changed.
Every aggregate repair figure was identical. A notebook-by-notebook
comparison found one structured difference, on 13 notebooks: both models
pinned \texttt{numpy} from the same grounded candidate list, Gemma to
1.26.3 and Qwen to 1.26.4, with no effect on installation, on the errors
exposed next, on Round 2, or on any final classification. Qwen completed
all 237 explanation records where Gemma completed 210. Because the model
and its serving environment changed together, that difference is reported
as an observation about the evaluation setup, not as evidence about model
architecture.

The final Gemma run's \texttt{repair\_attempts} table, one row per
repair-agent invocation of the full split, 235 in all, was also exported
and run through the existing RML mapping unchanged
(\Cref{sec:v-i6-fullscale}). This produced 3{,}478 triples, one
repair-attempt resource per row, each linked to the notebook resource that
the FAIR Jupyter knowledge graph uses for the repaired notebook, and all
24 validation checks passed in union with the existing notebook graph.
The benchmark table (O4) and the materialised repair graph (O6) therefore
describe the same 235 repair attempts; the repair graph has not been
loaded into the public FAIR Jupyter triple store.

Two things this chapter does not show are worth naming. It does not report
a repair success rate for the whole 214-row dataset, because 14 rows fall
outside pip-only repair scope by design (\Cref{chap:problem-dataset}). And
it does not compare the system against a baseline: a comparison against a
non-grounded repair agent remains future work (\Cref{chap:future-work}).

\Cref{sec:v-threats} states what this evaluation does and does not license
concluding, across internal, construct, external, and conclusion validity,
so the summary above is read with its boundaries attached.
