\chapter{Introduction}
\label{chap:introduction}

\section{Motivation}
\label{sec:intro-motivation}

Jupyter notebooks combine code, explanatory text, and results in a single
document. This makes them a popular way to share computational research,
especially in data-heavy fields such as biomedicine. A notebook published
alongside a paper is meant to let another researcher see, and re-run, exactly
how a result was produced.

In practice, many published notebooks do not run at all when someone else
tries them. Pimentel et al.~\cite{pimentel2019msr} collected 1.4~million
notebooks from GitHub and attempted to execute a large subset of them: only
24.11\% ran without errors, and only 4.03\% reproduced the results reported by
their original authors. Samuel and Mietchen~\cite{samuel2024gigascience}
found a similar pattern specifically for notebooks accompanying biomedical
publications on PubMed Central, the domain this thesis also builds on. These
numbers show that non-reproducible notebooks are not a rare exception; they
are the common case.

A large share of these failures is caused by dependencies, not by mistakes in
the underlying research logic. A notebook is written against a particular set
of installed Python packages. When it is later run in a different
environment, a package may be missing entirely, or a newer version of a
package may no longer provide the exact function the notebook expects. Both
situations produce an error before the notebook can finish, even though the
scientific code itself may be correct.

\begin{sloppypar}
The resulting error messages are short and technical, for example
\texttt{ModuleNotFoundError: No module named 'sklearn'}. A researcher who
is not a software developer may not know from the message alone that the
fix is to install a package called \texttt{scikit-learn}, not
\texttt{sklearn}.
\end{sloppypar}

\section{The FAIR Jupyter Pipeline and Its Remaining Gap}
\label{sec:intro-gap}

The FAIR Jupyter project has studied this problem at scale. Samuel and
Mietchen~\cite{samuel2024gigascience} built a pipeline that downloads
notebooks referenced by biomedical publications, executes them, and records
whether each notebook ran and, if not, what error occurred. The results were
organised into a queryable knowledge graph~\cite{samuel2024fairkg} so that
patterns in notebook reproducibility could be studied directly. A more recent
extension of the same pipeline~\cite{samuel2025docker} runs every repository
inside its own Docker container before execution. Containerisation removes
many failures that were really about a missing system tool or an
incompatible operating system, rather than about the research code.

Even this containerised pipeline stops at the point of \emph{detecting} a
failure. When a notebook still does not run inside its container, the
pipeline records the exception type and message and moves on. It does not
explain the failure to a human reader, and it does not attempt a fix. Every notebook whose only problem is a missing or outdated Python
package is left exactly as broken as it was found. Yet such problems
are, in principle, straightforward to repair, by installing or pinning
the right package version.

This is the gap this thesis addresses: turning a detected, dependency-related
notebook failure into an explained and, where possible, repaired one,
automatically and without a person in the loop for every single notebook.

\section{Contribution of This Thesis}
\label{sec:intro-contribution}

This thesis adds a repair layer on top of the existing Docker-based FAIR
Jupyter pipeline. The pipeline's own contribution ends at logging a
failure. This thesis begins exactly there. Given a notebook execution
that failed with a dependency-related error, the added layer performs
five steps:

\begin{enumerate}
  \item \textbf{Classify} the failure: is it really a dependency problem, and
        if so, is it a missing package or an incompatible version?
  \item \textbf{Explain} the failure in plain language, so that a researcher
        without a programming background can understand what went wrong.
  \item \textbf{Propose a repair}, using an open, locally-run large language
        model (LLM) whose suggestion is grounded in live package metadata
        from the Python Package Index (PyPI) rather than left to guess a
        version number from training data.
  \item \textbf{Apply the repair} inside a Docker environment rebuilt from
        the same recipe the notebook originally ran under, and re-run the
        whole notebook from the beginning.
  \item \textbf{Record the outcome}: whether the notebook now runs further,
        still fails, or could not be meaningfully tested.
  \end{enumerate}

When re-execution exposes a new dependency error that was hidden behind
the first, the layer classifies and explains that error too and, if it is
repairable, attempts one bounded second repair round. Two rounds is the
cap.

Grounding the repair suggestion in live PyPI data follows PLLM, the
closest prior system to this one. Bartlett et al.~\cite{bartlett2025pllm}
show that retrieval-augmented generation (RAG) against live package data
measurably improves an LLM's dependency-repair accuracy, compared to
letting the model rely on what it happens to remember from training.
This thesis adopts the same principle, but applies it inside a
reproducibility pipeline rather than to standalone Python scripts. It
also adds an explanation step and a re-execution-based validation step,
neither of which PLLM has.

\subsection{Research Questions}
\label{sec:intro-rqs}

The objectives say what was built. Three research questions say what the
evaluation in \Cref{chap:validation} asks of it, and \Cref{chap:conclusion}
answers each in turn.

\begin{description}
  \item[RQ1.] To what extent can an open LLM produce understandable,
    structured explanations of the residual dependency-related failures
    recorded by the FAIR Jupyter pipeline? This is answered on two levels:
    automatically, by how many explanation calls completed and how many
    completed responses satisfied the explanation schema, and by a human
    study of how readers rated the explanations.
  \item[RQ2.] How effectively can a PyPI-grounded, bounded repair pipeline
    resolve the targeted dependency error, and how often does that restore
    complete notebook execution? The two halves are kept apart throughout:
    targeted-error resolution is measured per repair attempt, full notebook
    recovery per notebook.
  \item[RQ3.] How sensitive are the structured repair decisions and the
    measured repair outcomes to the choice of open LLM, when the deterministic
    retrieval, validation, and execution pipeline is held fixed and only
    model- and provider-specific serving settings change?
\end{description}

\subsection{Summary of Results}
\label{sec:intro-status}

All six objectives were implemented. The 187-row evaluation split
described in \Cref{chap:problem-dataset} was reserved from prompt and
repair-strategy tuning, and the results reported in \Cref{chap:validation}
were generated by the final frozen implementation over that split, with a
two-round budget, a real local language model (Gemma-2 9B), the live PyPI
registry, and real Docker execution throughout. Four results frame the
rest of this thesis and answer the three research questions.

First (RQ1), the explainer completed 160 of the 187 original-failure
explanations and all 50 explanations of errors newly exposed by a first
repair; every completed response satisfied the explanation schema, and
the 27 missing ones were timeouts or a service error of the local model
deployment. A separate human study found the original-failure
explanations generally well received: 15 participants gave 540 ratings,
of which 88.9\% were Agree or Strongly Agree. Second (RQ2), 62 of the 73
repair attempts actually made (84.9\%) removed the specific dependency
error they targeted, and every repair proposal the model produced was
schema-valid and grounded in retrieved PyPI evidence. Third (RQ2 again),
no notebook in the evaluation split re-executed cleanly within the
two-round budget. End-to-end recovery was limited by the repair agent's
package mapping, which resolved the failing import often enough to reach
the model in under a third of its invocations, and by the fact that many
evaluated notebooks exposed further dependency errors in sequence.
Fourth (RQ3), repeating the evaluation
with a different open model, Qwen3.6-35B-A3B-MLX-8bit, left every
aggregate repair figure unchanged; the two models differed on 13
notebooks in which compatible NumPy release they selected to pin, with no
effect on any measured repair outcome. \Cref{chap:validation} reports all four
in full.

\section{Thesis Structure}
\label{sec:intro-structure}

\Cref{chap:related-work} reviews prior work on notebook reproducibility,
automated dependency resolution, and LLM-based program repair, and states
the specific gap this thesis fills. \Cref{chap:problem-dataset} describes the
scale of the reproducibility problem and how the concrete working dataset for
this thesis was obtained. \Cref{chap:architecture} presents the system
architecture: the five components introduced above, their contracts, and the
data they exchange. \Cref{chap:methodology} is the core of the thesis: it
explains, component by component, how each part was actually built and the
decisions made along the way. \Cref{chap:validation} reports the automated
test suite, the real-system pilots run during implementation, the final
evaluation over the 187-row evaluation split, the model-sensitivity
experiment, the human evaluation of explanation quality, and the threats to
validity that bound all of these. \Cref{chap:future-work} sets out what
remains open. \Cref{chap:conclusion} closes the thesis by answering the
three research questions.
