\section{Motivation}
\label{sec:intro-motivation}

Jupyter notebooks combine code, explanatory text, and results in a single
document. This makes them a popular way to share computational research,
especially in data-heavy fields such as biomedicine. A notebook published
alongside a paper is meant to let another researcher see, and re-run, exactly
how a result was produced.

In practice, many published notebooks do not run at all when someone else
tries them. Pimentel et al.~\cite{pimentel2019msr} collected 1.4~million
notebooks from GitHub and attempted to execute a large subset of them: only
24.11\% ran without errors, and only 4.03\% reproduced the results reported by
their original authors. Samuel and Mietchen~\cite{samuel2024gigascience}
studied notebooks accompanying biomedical publications on PubMed Central, the
domain this thesis also builds on. Of 10,388 re-executed notebooks, 1,203
(11.6\%) ran without an error and 879 (8.5\%) produced results identical to
those stored in the original notebook. These numbers show that execution failures 
were common in the notebooks examined by these studies.

Many notebook execution failures are dependency-related and occur before the
analysis logic can be evaluated~\cite{pimentel2019msr,samuel2024gigascience}.
A notebook is written against a particular set of installed Python packages.
When it is later run in a different environment, a package may be missing
entirely, or a newer version of a package may no longer provide the exact
function the notebook expects. Both situations stop execution before results can
be produced; the error alone does not show whether the underlying analysis is
correct.

\begin{sloppypar}
The resulting error messages are short and technical, for example
\texttt{ModuleNotFoundError: No module named 'sklearn'}. A researcher who
is not a software developer may not know from the message alone that the
fix is to install a package called \texttt{scikit-learn}, not
\texttt{sklearn}.
\end{sloppypar}

Large language models (LLMs) can help where a technical error message alone is
not enough. In this pipeline, an LLM explains a dependency failure in plain
language, helps interpret the relationship between an import name and a Python
package, and can suggest a possible package when the pipeline cannot identify
one directly. Open-weight LLMs are particularly suitable because they can run
on local or institutional hardware instead of requiring a proprietary external
API.

The model is not treated as an unquestioned source of repair commands. Package
information and notebook re-execution are used to check its suggestions before
a repair is accepted. This combines the language-understanding ability of an
LLM with an evidence-based repair process.

\section{The FAIR Jupyter Pipeline and Its Remaining Gap}
\label{sec:intro-gap}

The FAIR Jupyter project has studied this problem at scale. Samuel and
Mietchen~\cite{samuel2024gigascience} built a pipeline that downloads
notebooks referenced by biomedical publications, executes them, and records
whether each notebook ran and, if not, what error occurred. The results were
organised into a queryable knowledge graph~\cite{samuel2024fairkg} so that
patterns in notebook reproducibility could be studied directly. A more recent
extension of the same pipeline~\cite{samuel2025docker} reconstructs each
repository in a Docker environment before execution. It also infers
dependencies from notebook imports and adds them to the repository dependency
configuration. The remaining failures therefore represent notebooks that
still do not execute after these upstream preparation steps.

The recorded Docker run used in this thesis has the funnel shown in
\Cref{tab:intro-docker-funnel}. Of the 443 notebook executions from 83
repositories, 59 completed successfully without an error and 384 recorded
an error. Dependency errors form the largest recorded failure category, with
214 recorded dependency-error executions. If every one of these 214 notebook
executions could be made fully
successful, and no other outcome changed, the success rate would increase
from 13.3\% (59/443) to 61.6\% (273/443). This is a theoretical upper
bound of 48.3 percentage points, rather than an expected result, because
removing the first dependency error can reveal a later dependency or
non-dependency error.

Even this containerised pipeline stops at the point of \emph{detecting} a
failure. When a notebook still does not run inside its container, the
pipeline records the exception type and message and moves on. It does not
explain the failure to a human reader or attempt a repair. Some failures have
a local cause that is within this thesis's scope, such as a missing
third-party Python package or an incompatible package version. Repairing the
first error does not necessarily make the whole notebook executable: it can
reveal another dependency error, or a different kind of error, later in
execution. For this reason, every approved repair is checked by re-executing
the complete notebook, and the pipeline attempts at most two repair rounds.

This is the gap this thesis addresses: turning a detected dependency-related
notebook failure into an explained and, where supported by sufficient
evidence, repaired one without requiring manual investigation of every
notebook.

\section{Contribution of This Thesis}
\label{sec:intro-contribution}

This thesis adds a repair layer on top of the existing Docker-based FAIR
Jupyter pipeline. The pipeline's own contribution ends at logging a
failure. This thesis begins exactly there. Given a notebook execution
that failed with a dependency-related error, the added layer performs
five steps:

\begin{enumerate}
  \item \textbf{Classify} the failure: identify the failing import and
        determine whether the error is within the pip-based repair scope.
  \item \textbf{Explain} the failure in plain language, so that a researcher
        without a programming background can understand what went wrong.
  \item \textbf{Derive a repair proposal}, using verified PyPI package
        information and, where language-based judgement is needed, an open,
        locally run LLM. The proposal is checked before it is applied.
  \item \textbf{Apply the repair} at the recorded repository commit in its
        Docker environment, and re-run the whole notebook from the beginning.
  \item \textbf{Record the outcome}: whether the notebook now runs further,
        still fails, or could not be meaningfully tested.
  \end{enumerate}

When re-execution exposes a new dependency error that was hidden behind
the first, the layer classifies and explains that error too and, if it is
repairable, attempts one bounded second repair round. Two rounds is the
cap.

PLLM is the closest prior system to this work. Bartlett et
al.~\cite{bartlett2025pllm} show that retrieval-augmented generation (RAG)
over package data can support LLM-based dependency repair. Both PLLM and this
thesis validate a proposed repair through execution feedback. The key
difference is the unit of operation: PLLM targets standalone Python files,
whereas this thesis operates on notebook failures recorded by the FAIR Jupyter
pipeline. The present pipeline also reconstructs a repository-specific Docker
environment, limits repair to two rounds, provides a human-readable
explanation, and records structured outcomes for knowledge-graph export. A
direct execution of PLLM would therefore not provide a like-for-like notebook
comparison; \Cref{sec:v-pllm-comparison} uses a notebook-adapted PLLM-style
baseline instead.

\subsection{Research Questions}
\label{sec:intro-rqs}

The objectives say what was built. Three research questions say what the
evaluation in \Cref{chap:validation} asks of it, and \Cref{chap:conclusion}
answers each in turn.

\begin{description}
  \item[RQ1.] To what extent can an open LLM produce understandable,
    structured explanations of the residual dependency-related failures
    recorded by the FAIR Jupyter pipeline?

  \item[RQ2.] How effectively can a PyPI-grounded, bounded repair pipeline
    resolve the targeted dependency error, and how often does that restore
    complete notebook execution?

  \item[RQ3.] How sensitive are the structured repair decisions and the
    measured repair outcomes to the choice of open LLM, when the deterministic
    retrieval, validation, and execution pipeline is held fixed and only
    model- and provider-specific serving settings change?
\end{description}

\subsection{Summary of Results}
\label{sec:intro-status}

The 187-record evaluation split described in \Cref{chap:problem-dataset}
was reserved from prompt and repair-strategy tuning. The live-PyPI evaluation
used Gemma-2~9B, a two-round budget, and repository-specific Docker
re-execution. The following results frame the rest of this thesis.

For RQ1, the explainer completed 180 of the 187 explanations of original
failures and all 69 explanations of errors newly exposed after a first repair.
A separate user study found the explanations generally well received: 15
participants gave 540 ratings, of which 88.9\% were Agree or Strongly Agree.
A separate blinded comparison with 15 participants rated resolver-informed
template explanations higher than LLM explanations on all six items for four
selected errors. Both studies are descriptive convenience samples.
For RQ2, the pipeline recovered five notebooks from start to finish. The
remaining records show why end-to-end recovery is difficult: some required a
safe abstention, some could not be tested successfully in Docker, and others
revealed further errors during execution.

In a matched comparison using the same frozen PyPI release metadata, the
notebook-adapted PLLM-style baseline recovered six notebooks and the thesis
pipeline recovered three; two recoveries were shared. The thesis pipeline
resolved its targeted error in 63.2\% of Docker repair attempts, compared
with 53.1\% for the baseline. This single descriptive comparison shows
different trade-offs, rather than an overall winner.

For RQ3, the same frozen-metadata evaluation was also run with Qwen in place
of Gemma. Qwen produced valid structured explanations for 261 of 262
encountered errors, compared with 238 of 264 for Gemma. Both models recovered
three notebooks. The small difference in targeted-error resolution cannot be
attributed to model choice alone because the serving environments and two
Docker outcomes differed between the runs.

\section{Thesis Structure}
\label{sec:intro-structure}

\Cref{chap:related-work} reviews prior work on notebook reproducibility,
automated dependency resolution, and LLM-based program repair, and states
the specific gap this thesis fills. \Cref{chap:problem-dataset} describes the
scale of the reproducibility problem and how the concrete working dataset for
this thesis was obtained. \Cref{chap:architecture} presents the system
architecture: the five components introduced above, their contracts, and the
data they exchange. \Cref{chap:methodology} is the core of the thesis: it
explains, component by component, how each part was actually built and the
decisions made along the way. \Cref{chap:validation} reports the automated
test suite, the real-system pilots run during implementation, the final
evaluation over the 187-row evaluation split, the model-sensitivity
experiment, the human evaluation of explanation quality, and the threats to
validity that bound all of these. \Cref{chap:future-work} sets out what
remains open. \Cref{chap:conclusion} closes the thesis by answering the
three research questions.
