\chapter{System Architecture}
\label{chap:architecture}

This chapter describes the architecture of the automated explanation and
repair workflow developed in this thesis. The workflow is separate from the
FAIR Jupyter pipeline: it uses dependency-error records produced by the
Docker-based FAIR Jupyter execution process as input, but it does not modify
that upstream process. Starting from a recorded dependency failure, it
classifies the error, explains it, derives a possible repair, re-executes the
notebook in Docker, and records the outcome in a structured form.

The workflow is a \emph{procedural pipeline}: a deterministic orchestrator
runs a fixed sequence of components in a defined order. This is suitable for
batch processing because each decision and outcome can be recorded and
checked. It differs from interactive notebook-repair approaches, which assume
a live kernel and a user who can guide the repair process
\cite{grotov2024untangling,grotov2024debug}.

When re-execution exposes a new eligible dependency error, the orchestrator
permits one additional repair round. This two-round budget bounds the number
of Docker re-executions; it does not claim to measure the maximum recovery
possible with further rounds. Its implementation and limitation are discussed
in \Cref{sec:m-orchestrator-round2}.

The LLM has limited roles in this workflow. It produces a plain-language
explanation for each classified error. For repair, it may suggest one
distribution name when deterministic matching cannot identify a package, and
it may choose between several versions that have already been verified as
candidates. A suggested distribution is accepted only after verification with
PyPI and wheel-import evidence. Docker re-execution, not the LLM, determines
whether a proposed repair worked.

The architecture follows the functional and non-functional requirements
defined in \Cref{tab:rw-requirements}, which provide the criteria used to
design and assess the workflow.

This chapter defines what each component receives, what it does, and what it
passes to the next component. Prompt design, model configuration, PyPI
retrieval, and implementation details are described in
\Cref{chap:methodology}.

\section{Design Overview}
\label{sec:design-overview}

The workflow can be summarised as follows: when a notebook fails because of
a dependency error, the system reads and classifies the recorded failure,
generates a plain-language explanation, determines whether a supported repair
can be proposed from verified package evidence, applies an approved repair,
re-executes the notebook in Docker, and records the outcome. The workflow
contains five components coordinated by an orchestrator. The relationship
between the thesis objectives, workflow components, research questions, and
evaluation evidence is given in \Cref{tab:intro-objectives}. The following
sections explain how these components work together as one workflow.

\section{Integration Point}
\label{sec:integration-point}

\begin{sloppypar}
The containerised FAIR Jupyter pipeline~\cite{samuel2025docker}
executes the notebooks of each repository inside a per-repository
Docker container. It writes one row per execution to the
\texttt{notebook\_executions} table, and tags each failure with an
\texttt{error\_category}. A pre-existing categorisation routine
(\texttt{summary.py}) already maps \texttt{ModuleNotFoundError} and
\texttt{ImportError} to \texttt{DEPENDENCY\_ERROR}. The repair layer
activates on exactly those rows: it performs a batch pass over the
\texttt{notebook\_executions} rows whose \texttt{error\_category =
DEPENDENCY\_ERROR}. The repair workflow reads these rows as input; it does
not modify the upstream FAIR Jupyter execution process.
\end{sloppypar}

\paragraph{Re-execution environment.}
FixApplicator does not reopen the Docker container that produced the original
failure, because that temporary container was not retained by the upstream
execution process. Instead, for each approved repair, it clones the repository
into a fresh working directory, checks out the commit recorded for that
repository, and creates a new Docker build context. The resulting container
uses the configured Python base image and follows the same general dependency
installation procedure as the upstream Docker pipeline
(\Cref{sec:m-fixapply-docker}). It installs the repository dependencies,
applies the approved repair, and executes the notebook again from its first
cell.

This procedure reproduces the repository source revision used for the recorded
failure, but it does not reproduce the historical environment exactly. The
upstream execution did not retain a complete package inventory or the Docker
image digest. Consequently, unpinned dependencies can still resolve
differently when the repair is tested. Each repair trace records the repository
commit and commit-checkout status so that this limitation remains visible.

\begin{sloppypar}
\paragraph{Context available at the hook-in point.}
Three kinds of context are distinguished. Directly available, from the
Docker pipeline's result row, are
\texttt{error\_type}, \texttt{error\_message}, \texttt{error\_cell\_index},
\texttt{notebook\_id}, \texttt{repository\_id}, \texttt{notebook\_name},
\texttt{url}, \texttt{total\_code\_cells}, \texttt{executed\_cells}
(and \texttt{error\_category}); these form the raw input to the repair
layer. Additional context can be recovered when needed. A legacy execution table
may provide a traceback, and the notebook source can be fetched again from
GitHub (\Cref{sec:m-classification}). These sources are treated with lower
confidence because they may not correspond exactly to the original failed
execution. The original repository clone and Docker container were not
preserved. FixApplicator therefore clones the repository again for repair
validation. When a recorded repository commit is available, it checks out that
exact revision before building the Docker environment. If no commit is
available, this is explicitly recorded; if a recorded commit cannot be checked
out, the attempt is reported as an infrastructure failure rather than silently
tested against a different revision.
\end{sloppypar}

\paragraph{Working set.}
The rows the repair layer activates on are the 214
\texttt{DEPENDENCY\_ERROR} records of \Cref{chap:problem-dataset}, of which
200 fall inside the pip-only repair scope. Those counts, the subtypes
behind them, and the development/evaluation split of the 200 are all fixed
there and are not restated in this chapter.

\noindent
\Cref{fig:architecture-components} shows the fixed control flow of the
workflow. The orchestrator, rather than an autonomous LLM agent, determines
which component runs next. The LLM produces explanations and has narrowly
defined roles in repair decisions, while verified package evidence and Docker
re-execution determine whether a repair may be proposed and whether it worked.

Each component is defined below by what it does and by its input/output
contract. Its relationship to the thesis objectives and evaluation evidence
is given in \Cref{tab:intro-objectives}. Implementation is deferred to
\Cref{chap:methodology}.

\subsection{ErrorClassifier}
\label{subsec:errorclassifier}
ErrorClassifier determines whether a recorded failure is within the
pip-based repair scope and extracts its failing module and subtype. It uses the
upstream error category as an initial filter and applies the same decision when
re-execution exposes a new error.\\
\textbf{Input.} A \texttt{notebook\_executions} row (the fields listed in
Section~\ref{sec:integration-point}), or, in the second round, the new
error type and message that FixApplicator observed after re-execution.\\
\textbf{Output.} A classification carrying three values:
\texttt{failing\_module}, \texttt{subtype}, and \texttt{scope\_status}.
\texttt{scope\_status} controls whether the repair components run, not
whether the error is explained: excluded and out-of-scope failures are still
sent to LLMExplainer. The subtype taxonomy and classification rules are given
in \Cref{chap:problem-dataset,sec:m-classification}.

\subsection{LLMExplainer}
\label{subsec:llmexplainer}
LLMExplainer generates a plain-language explanation of the classified
error for a non-expert reader (NFR2).\\
\textbf{Input.} One classified record, including the error type, message,
failing module, and available cell-level context.\\
\textbf{Output.} A schema-validated explanation and the identifier of the
model that produced it.\\
The explanation is reader-facing: RAGRepairAgent does not receive it, and a
failed explanation call does not prevent an otherwise eligible repair. Prompt
and model settings are specified in \Cref{chap:methodology}.

\subsection{RAGRepairAgent}
\label{subsec:repairagent}
RAGRepairAgent makes the repair decision for a classified, repair-eligible
error using verified package evidence.\\
\textbf{Input.} The classified error record, configured package evidence, and
any relevant repository dependency declaration.\\
\textbf{Output.} A \emph{fix object} (Section~\ref{subsec:fix-object}), or
an abstention when the available evidence is insufficient to support a
repair.\\
\textbf{Limited LLM role.} The LLM may propose one additional distribution
when deterministic resolution cannot verify a candidate, or choose among
already verified compatible versions. Every proposed repair must be verified
before it is applied. A declaration such as \texttt{requirements.txt} is
context, not proof that a distribution provides an import. The retrieval and
verification procedure is specified in \Cref{sec:m-repair}.

\subsection{FixApplicator}
\label{subsec:fixapplicator}
FixApplicator applies the validated repair inside a rebuilt Docker
environment and re-executes the notebook to check whether the repair
worked. It always runs the notebook from its first cell.\\
\textbf{Input.} A fix object together with the notebook and repository
information needed to rebuild the execution environment.\\
\textbf{Output.} An outcome
$\in \{\texttt{fixed},\ \texttt{still\_failing},\ \texttt{apply\_error}\}$,
with the new error type and message when execution still fails, and an
indication of whether that error matches the one targeted by the repair.
\texttt{fixed} means that the notebook completed from its first cell without
an execution error. Docker reconstruction and Round-2 handling are described
in \Cref{sec:m-fixapply-docker,sec:m-fixapply-round2}.

\subsection{ResultLogger}
\label{subsec:resultlogger}
ResultLogger persists structured repair-attempt data. It is the source of
the evaluation dataset and the CSV input to the knowledge-graph mapping; it
does not write RDF itself.\\
\textbf{Input.} The classification, explanation, fix object, outcome, and
run metadata of one repair-decision entry.\\
\textbf{Output.} One \texttt{repair\_attempts} row per repair-decision
entry, whether the workflow applies a fix, abstains, or excludes the record
from repair. The record retains the explanation status in every case. Its CSV
export is later used to materialise and structurally validate repair RDF.
The logging schema and RDF process are described in
\Cref{sec:m-resultlogger,subsec:kg}.

\section{Orchestration and Control Flow}
\label{sec:orchestrator}

The orchestrator coordinates the components for each input record in a fixed
order: classify, explain, decide whether repair is eligible, construct and
validate a repair proposal, apply an approved repair, and log the result. It
does not reimplement component logic. Its own responsibilities are to maintain
a shared run identifier, isolate failures in individual records, and control
the optional second repair round.

\paragraph{The bounded second round.}
A second round is considered only after FixApplicator has applied a Round-1
repair and re-execution exposes a genuinely different, repair-eligible
dependency error. That error is classified and explained as a new record
before it receives a second repair decision. The Round-2 environment retains
the approved Round-1 repair, so both repairs are tested together. No third
repair round is started.

The two-round limit is a bounded engineering decision: it limits Docker
re-execution cost and prevents an unbounded repair loop. It is not evidence
that further rounds would not recover additional notebooks. The effect of a
larger round budget remains future work (\Cref{sec:fw-coverage}).

\paragraph{Failure isolation (NFR4).}
Every record is handled independently. A component failure, such as malformed
LLM output, unavailable package evidence, or a Docker timeout, is recorded
for that record and does not abort the remaining batch.

\paragraph{Configuration surface (NFR5).}
The model, prompt strategy, package-evidence configuration, and round budget
are supplied per run rather than hard-coded. The implementation of this
control flow, including the exact Round-2 trigger and trace handling, is
described in \Cref{sec:m-orchestrator-round2}.

\section{Data Contracts}
\label{sec:data-contracts}

\subsection{Fix Object}
\label{subsec:fix-object}

The RAGRepairAgent emits the \emph{proposed} fix as structured JSON,
before application. The repair scope is pip-only: \texttt{action} is one of
\texttt{install}, \texttt{pin\_version}, or \texttt{none}; \texttt{version}
is \texttt{null} for a plain install; and \texttt{command} is exactly what
the FixApplicator runs inside the container. Notebook-code edits
(such as \texttt{replace\_import}) are outside the scope of this thesis.

The example below is based on notebook-execution record~198 from the
evaluation dataset. Its \texttt{ImportError} was repaired by selecting the
verified version \texttt{numpy==1.24.1}. The listing presents the meaningful
content of the fix object rather than every literal persisted field name.
The implemented trace (\Cref{sec:m-repair}) also records the evidence and
the relevant dependency declaration.

\begin{verbatim}
{
  "action": "pin_version",
  "import_name": "numpy",
  "install_name": "numpy",
  "version": "1.24.1",
  "command": "python -m pip install numpy==1.24.1",
  "rationale": "A verified compatible NumPy version was selected
                for the recorded wrong-version error.",
  "pypi_evidence": {
    "chosen_version": "1.24.1",
    "requested_import": "numpy",
    "wheel_provides_import": true
  }
}
\end{verbatim}

\subsection{The \texttt{repair\_attempts} Table}
\label{subsec:repair-table}

The repair layer stores its trace in one SQLite table named
\texttt{repair\_attempts}. Each database row records one repair decision for
one error and, where a repair is applied, the result of re-executing the
notebook. The table is both the validation log for O3 and the reusable repair
dataset for O4.

There is one row for each repair decision. If the pipeline cannot justify a
safe repair, it records \texttt{action = none}; because no command is run,
the outcome is empty. If the first repair exposes a different eligible
dependency error, the second-round decision is stored as a second row for
the same original notebook execution. Records outside the repair scope also
receive an abstention row, even though they do not reach the repair agent.
Consequently, every original error is represented and some errors have more
than one row. The error itself is not copied: \texttt{notebook\_execution\_id}
links each row to the originating failure.

The table also records the model, prompt strategy, round, and run identifier.
These fields make it possible to distinguish results from different
experimental configurations. Counts and outcomes are reported in
\Cref{chap:validation}.

\begin{table}[t]
\centering
\small
\begin{tabular}{p{0.24\textwidth}p{0.67\textwidth}}
\hline
\textbf{Field group} & \textbf{Purpose} \\
\hline

Explanation and decision & \texttt{explanation}, \texttt{action}, \texttt{install\_name}, \texttt{version}, \texttt{command}, \texttt{rationale}, \texttt{pypi\_evidence}, and \texttt{declared\_constraint} record why a repair was, or was not, proposed. \\

\begin{verbatim}
CREATE TABLE repair_attempts (
  id                      INTEGER PRIMARY KEY,
  notebook_execution_id   INTEGER NOT NULL,

  -- from ErrorClassifier
  failing_module          TEXT,          -- e.g. "scanpy"
  subtype                 TEXT,          -- classifier subtype

  -- from LLMExplainer (O1): this round's explanation
  explanation             TEXT,

  -- from RAGRepairAgent -- the proposed fix (O2)
  action                  TEXT,   -- install | pin_version | none
  install_name            TEXT,          -- resolved PyPI name
  version                 TEXT,   -- version to pin, or NULL
  command                 TEXT,          -- exact command run
  rationale               TEXT,
  pypi_evidence           TEXT,   -- JSON retrieval evidence
  declared_constraint     TEXT,   -- JSON declaration context

  -- from FixApplicator -- the outcome (O3)
  outcome                 TEXT,   -- fixed|still_failing|apply_error
  new_error_type          TEXT,
  new_error_message       TEXT,

  -- run metadata (for experiments)
  llm_model               TEXT,
  prompt_strategy         TEXT,          -- for prompt comparison
  round                   INTEGER,       -- 1 or 2 (hard cap)
  run_id                  TEXT,   -- groups one run / config
  created_at              TEXT
);
\end{verbatim}

The listing contains nineteen fields besides the row identifier. Their values
are assembled from the upstream output files as described in
\Cref{sec:m-resultlogger}. The SQLite schema does not enforce the link to the
classifier data as a database foreign key. Instead, the logger checks that
every \texttt{notebook\_execution\_id} exists before writing a row. Repeated
identifiers are valid: they represent separate decisions for the same
notebook execution and are deliberately kept as separate rows.

\subsection{Knowledge-Graph Enrichment}
\label{subsec:kg}

The database trace is useful for the pipeline itself. The RDF export makes
the same repair information available as a graph that can be linked to FAIR
Jupyter~\cite{samuel2024fairkg}. In this graph, a notebook is connected to
the repair attempts made for its failed execution. A researcher can then see
both the original reproducibility record and the later repair history through
the same notebook identifier.

Objective~O6 adds an RML mapping for \texttt{repair\_attempts}. RML is a
set of rules that converts table rows into RDF triples. The mapping is based
on FAIR Jupyter's existing execution mapping: for each repair row, it creates
a repair-attempt resource and links it to the existing notebook resource.
Morph-KGC runs these rules from the project's build script. Reusing this
CSV-based process means that the repair data is generated with the same
tooling as the rest of the graph.

The vocabulary is kept simple. Existing \texttt{repr:} terms are reused when
they already describe a fact, such as a post-repair exception. New
\texttt{repr:} terms describe repair-specific facts, such as the failing
module and repair outcome. PROV-O~\cite{provenance2013} describes each repair
attempt as an activity with a completion time. The base IRI is
\texttt{repr:}~$=$~\url{https://w3id.org/reproduceme/}, and the output format
is Turtle (\texttt{.ttl}).

The repair RDF is materialised and structurally validated in this work. It
has not been loaded into a public triple store, so public graph queries are
not evaluated here. The export supports later reuse, in line with the
provenance emphasis of FAIR4RS~\cite{barker2022fair4rs}, but it does not by
itself demonstrate that all FAIR principles have been met.

\begin{verbatim}
repr:notebook_453  repr:hadRepairAttempt  repr:repairattempt_001 .

repr:repairattempt_001
    a                       prov:Activity, repr:RepairAttempt ;
    repr:failingModule      "numpy" ;                 # new term
    repr:fixCommand         "python -m pip install numpy==1.24.1" ;
    repr:fixOutcome         "fixed" ;
    repr:llmModel           "gemma2:9b" ;
    prov:endedAtTime        "2026-09-25T05:30:13Z"^^xsd:dateTime .
\end{verbatim}

The example uses the repair values from record~198. The first line links
notebook~453 to a repair attempt. The remaining lines describe that attempt:
the failed import was \texttt{numpy}, the applied command installed
\texttt{numpy==1.24.1}, and the notebook was fixed. The identifier
\texttt{repairattempt\_001} is a stand-in for the row identifier assigned at
export time. If a repair still fails, the mapping also records the
\emph{post-repair} exception and message with \texttt{repr:exception} and
\texttt{repr:msg}. The dependency-declaration context remains in the SQLite
and CSV trace; the current RML mapping does not export that field.

\section{Demonstration Interface}
\label{sec:demo-interface}

A demonstration interface accompanies the pipeline so that a single repair can
be followed from the original failure to the final verdict without reading raw
trace files. It is a small static web application with two views. A record
list covers every notebook of one recorded run and can be filtered by the
decision path a record took. Selecting a record opens a trace view that walks
that notebook through the stages this chapter has defined, grouped into
reading the failure, grounding a repair, and applying it.

The interface is a visualisation layer, not a further pipeline component. It
reads the stored artefacts of a completed run -- the round-by-round trace, the
classifier context and the run manifest -- and renders them unchanged. It
issues no request of its own to Ollama, PyPI, GitHub or Docker, no control in
it executes a repair, and nothing it displays can alter a recorded decision.
The figures below are taken from the recorded run
\texttt{v2-evaluation-20260925T013000Z}, produced with \texttt{gemma2:9b}
served by a local Ollama instance. The interface played no part in the
quantitative evaluation of \Cref{chap:validation}, and no usability evaluation
of the interface itself is claimed.

A repair is easiest to misread where one name is substituted for another, so
the interface assigns a fixed colour to each role a name can occupy: the
requested top-level import, a candidate distribution proposed by a mapping
source, a distribution verified against PyPI and wheel metadata, the repair
selected by RAGRepairAgent, the command FixApplicator applied, and the outcome
Docker reported. \Cref{fig:demo-records} shows the record list with that key
and with one highlighted record per decision path.

Together, these components define the repair-layer architecture:
classification and explanation establish what failed, RAGRepairAgent
proposes a grounded repair, FixApplicator validates it through
re-execution, and ResultLogger preserves the resulting evidence for
evaluation and knowledge-graph integration. \Cref{chap:methodology}
describes how these contracts were implemented, while
\Cref{chap:validation} evaluates the resulting system.
