Jupyter notebooks are widely used to share computational research, but
many published notebooks fail to re-execute in a different environment.
The FAIR Jupyter pipeline containerises each repository before execution,
yet it still only detects and logs the dependency-related failures that
remain. This thesis adds a layer that explains and repairs them.

The working dataset is the residual set of 214 dependency-related failures
recorded by the Docker-based pipeline. Of these, 200 fall inside a pip-only
repair scope, split into 13 development records and 187 evaluation records
reserved from prompt and repair-strategy tuning. A deterministic classifier
decides each failure's subtype and repair eligibility before any language
model is consulted. An explanation component produces a plain-language,
schema-validated description of every classified failure, whether or not
it can be repaired. A repair component proposes a fix with an open language
model whose suggestion is grounded in live metadata from the Python Package
Index and validated against that evidence, so a package name or version is
never invented. A fix-application component applies the proposal in a
Docker environment rebuilt from the original recipe, re-executes the whole
notebook, and classifies the result. When re-execution exposes a new
error, the layer classifies and explains it too and, if it is repairable,
attempts one bounded second repair round. Every repair-agent invocation is
logged in a SQLite benchmark table, and the final run's table was
materialised through an RML mapping as RDF linked to the notebooks of the
FAIR Jupyter knowledge graph. The implementation is covered by 711
automated tests.

The results were generated by the final frozen implementation over the
187 evaluation records with Gemma-2 9B. The explainer completed 160 of the
187 original-failure
explanations and all 50 explanations of newly exposed errors; every
completed response was schema-valid, and the 27 missing ones were runtime
timeouts or a service error of the local model deployment. Of the 73 real
repair attempts made across both rounds, 62 (84.9\%) removed the specific
dependency error they targeted, and all 73 repair proposals were
schema-valid and PyPI-grounded. No notebook re-executed cleanly from start
to finish within the two-round budget (0 of 187). Two limits explain this
gap: the static import-to-distribution mapping let only 73 of 235
repair-agent invocations reach the model, the rest abstaining, and
resolving one dependency error frequently exposed a further one.

Repeating the evaluation with Qwen3.6-35B-A3B-MLX-8bit in place of Gemma,
with the pipeline held fixed and only model-specific serving settings
changed, left every aggregate repair figure identical. The two models
differed on 13 notebooks in which compatible NumPy release they selected
to pin: Gemma chose 1.26.3 and Qwen 1.26.4 from the same grounded
candidate set, with no effect on any downstream repair outcome. Qwen completed
all 237 explanation records under its serving environment, whereas the
local Gemma run experienced runtime timeouts; since model and serving
setup changed together, this does not isolate the model as the cause.

In a separate human study, 15 participants each rated six explanations
drawn from a frozen pool of 12 original-failure explanations, on a
six-item explanation-satisfaction questionnaire (90 explanation
evaluations, 540 ratings): 88.9\% were Agree or Strongly Agree, every
item reached a majority-agree median, and satisfaction was the lowest
item, matching free-text requests for more detail about the likely cause.
