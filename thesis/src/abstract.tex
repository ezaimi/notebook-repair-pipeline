Jupyter notebooks are widely used to communicate computational research because
they combine code, explanatory text, data analysis, and results in one document.
They support transparent and reusable research only when other researchers can
re-execute them outside the original author's environment. In practice, this is
often difficult because notebooks depend on specific software packages and
package versions. A missing package or an incompatible version can stop
execution before the analysis is reached, while the resulting error message may
be too technical for a researcher without a software-development background.
The Docker-based FAIR Jupyter pipeline identifies such failures during notebook
re-execution, but it did not originally explain them or attempt to repair them.


This thesis presents an automated workflow for explaining and repairing
third-party Python dependency errors found in Docker-based FAIR Jupyter
execution records. It contains an error classifier, an LLM-based explanation
component, an evidence-grounded repair component, a Docker-based fix
applicator, and structured result logging. The workflow attempts to explain
every encountered dependency error in plain language, including errors outside
the repair scope. For repair-eligible cases, it combines
package information from PyPI with verified import evidence to select a safe
repair, applies it in the recorded repository environment, and re-executes the
notebook. One further repair round is allowed when execution exposes a new
dependency error. The evaluation uses 187 held-out dependency-error records.

A user study found that participants generally considered the explanations
understandable, useful, and correct. In a separate blinded comparison, readers
rated a resolver-informed deterministic explanation higher than the LLM
explanation for the four selected errors. In the live-PyPI evaluation, the workflow
recovered five notebooks from start to finish within the two-round limit. A
matched comparison with a notebook-adapted PLLM-style baseline, using frozen
PyPI metadata, found different strengths rather than an overall winner. The
model-sensitivity evaluation found that Qwen produced valid structured
explanations more reliably than the local Gemma deployment, while both models
recovered the same number of notebooks. The results show
that the approach can support researchers in understanding failures and
recovering some notebooks, while package installation alone cannot solve every
reproducibility problem. Future work can extend the approach to further error
types and repair actions beyond pip-based packages.
