\chapter{Remaining Work}
\label{chap:future-work}

This chapter states plainly what has not been built yet, so that nothing in
the preceding chapters is mistaken for a finished system. Result logging
and knowledge-graph enrichment, listed as remaining work in an earlier
draft of this chapter, have since been implemented and validated at pilot
scale (\Cref{sec:m-resultlogger,sec:v-i6}); full pipeline orchestration,
shared run-level metadata, and the bounded second repair round -- also
listed as remaining work in an earlier draft -- have likewise since been
implemented and validated by a small real pilot (see below). What is
listed here is what none of that work yet covers: running any of it,
unattended, over the full dataset, and the evaluation work that depends on
having done so. Confirmed by direct inspection rather than assumed.

\section{Remaining Implementation}

\paragraph{Full Pipeline Orchestration -- implemented.} \Cref{chap:architecture}
describes an orchestrator that loops over every usable row, running
classification, explanation, repair, fix application, and result logging
in sequence and logging every attempt, including ones where a component
itself fails. This loop is now implemented (\texttt{scripts/run\_pipeline.py})
and exercised end to end, with real Ollama, PyPI, and Docker calls, against
a small number of development-split records -- not yet the full 200-row
usable set (see "Full-Dataset Population" and "Full Evaluation Run"
below). Every component it calls -- ResultLogger included -- is called
through its existing, unmodified interface; building the orchestrator
required no redesign of any of them, only the two small, backwards-compatible
plumbing additions described next and in \Cref{chap:architecture}.

\paragraph{Shared Run-Level Metadata -- implemented.} The orchestrator
generates a single \texttt{run\_id} (shaped \texttt{i7-<UTC timestamp>}, or
an explicit override) once per invocation and passes it into every call to
LLMExplainer, RAGRepairAgent, and FixApplicator for every row and every
round that invocation processes. RAGRepairAgent and FixApplicator already
accepted an optional \texttt{run\_id} override before this change; no new
parameter was needed on either. Every \texttt{repair\_attempts} row an
orchestrated run writes now carries that same, genuinely shared, run
identifier. ResultLogger's own per-record fallback behaviour
(\Cref{sec:m-resultlogger-row}) is unchanged and still applies when a
repair attempt has no matching fix-application outcome to fall back to.

\paragraph{Bounded Second Repair Round -- implemented.} When FixApplicator
reports \texttt{still\_failing} with a genuinely new error
(\Cref{sec:v-key-observation}), the orchestrator now reclassifies that new
error with the same classifier used for every original dataset row, and
feeds it back into RAGRepairAgent for one further, bounded attempt --
capped at two rounds in total, regardless of configuration; a third round
is not reachable by any code path. Round 2 reuses RAGRepairAgent and
FixApplicator unmodified, targets only the newly-exposed failure (never
the original one), and re-applies Round 1's already-validated fix inside
the freshly rebuilt Round 2 container before applying Round 2's own fix,
so the notebook is re-executed against "original environment + Round 1 +
Round 2," not "original environment + Round 2 only." \texttt{repair\_attempts.round}
can now be \texttt{2}, and is, for the small pilot rows this chapter's
"Full-Dataset Population" paragraph describes; a full second round only
fires when the reclassified new error is itself pip-repair-eligible, which
a real pilot case (\Cref{chap:validation}) showed is not guaranteed even
when the new error is a genuine, different \texttt{missing\_package}
failure -- see that chapter for what was actually observed.

\paragraph{Full-Dataset Population of the Benchmark Table and Knowledge
Graph.} ResultLogger, the CSV export, and the RML mapping
(\Cref{sec:m-resultlogger}) are implemented and validated against real
pilot data (\Cref{sec:v-i6}), and the orchestrator that would drive them
over the full dataset now exists too, but none of them has been run over
the complete 200-row usable set. The \texttt{repair\_attempts} table and
the knowledge-graph triples derived from it currently hold only the small
number of pilot records reported in \Cref{chap:validation}, not the full
dataset. Populating them at full scale is now only a matter of invoking the
orchestrator above over every usable row, not of building anything further.

\section{Remaining Evaluation}

\paragraph{Full Evaluation Run.} The pilots in \Cref{chap:validation} cover
fewer than ten records in total. The 187-row evaluation split reserved in
\Cref{chap:problem-dataset} has not been run. The orchestrator needed to do
so now exists (see above) and is deliberately defaulted away from that
split during development to avoid consuming it prematurely; running it is
now a matter of invoking that orchestrator 187 times with
\texttt{-{}-split evaluation}, which has not been done.

\paragraph{One-Round versus Two-Round Comparison.} Comparing repair success
with and without the second repair round requires running the
now-implemented orchestrator's two-round mode over the full evaluation
split above and comparing it against a one-round run over the same split;
neither run has been performed yet.

\paragraph{Explanation Quality Evaluation.} The project plan includes a
user study with Likert-scale scoring of explanation quality and a Cohen's
kappa analysis of agreement between raters. This has not started; it
depends on having a stable set of generated explanations to show
participants, which \Cref{chap:validation} shows exists only for a handful
of pilot rows so far.

\paragraph{Baseline Comparison.} Comparing this system's repair success
rate against a baseline (for example, a version of the repair agent without
PyPI grounding) requires the full evaluation run above to exist first, so
the two can be compared on the same rows.

\paragraph{Benchmark Dataset Finalisation.} Objective O4 calls for
publishing the completed \texttt{repair\_attempts} table as a reusable
benchmark. The table's schema, population logic, and knowledge-graph
mapping are implemented and validated (\Cref{sec:m-resultlogger,sec:v-i6});
publishing it as a finished benchmark still requires the full-dataset
population above, which is the last step in the chain, since it depends on
every step before it.
