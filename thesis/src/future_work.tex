\chapter{Future Work}
\label{chap:future-work}

Chapter~6 evaluates the pipeline and identifies the next steps needed before it
could become a more widely usable repair service. The priorities are clear:
publish the locally materialised provenance graph, improve coverage without weakening the
evidence checks, repeat the evaluation under controlled conditions, and broaden
the reader study. None of these steps changes the central result of this thesis:
a repair should be accepted only after its evidence has been checked and its
effect has been tested in the repository environment.

\section{From a Validated Mapping to a Usable Repair Graph}
\label{sec:fw-kg}

The RML mapping and notebook-identity alignment were first validated on pilot
data in \Cref{sec:v-i6,sec:v-i6-fullscale}. The final live-PyPI run was then
materialised locally from the complete final-evaluation table and checked against
that source table. It has not, however, been published as an RDF graph. This
distinction is important: local materialisation shows that the mapping can
represent repair attempts correctly; it does not by itself provide a deployed
graph for other researchers to query.

The immediate next step is therefore to package and publish the already
materialised final-evaluation graph. The exported repair attempts, mapping,
generated triples, and validation report should be versioned with the input
manifest and software environment so that a later reader can reproduce,
inspect, and query the graph. The manifest described in
\Cref{sec:v-final-manifest} provides the identifiers and hashes needed to
connect that graph to the exact evaluation run.

A published graph should support questions that the evaluation tables currently
answer only after separate aggregation. For example, a query could identify
notebooks that reached Round~2, list modules for which the resolver abstained,
or compare outcomes across runs. Before more than one run is loaded, the
repair-attempt IRI should include the run identifier as well as the row
identifier. This prevents independently generated tables from creating the same
IRI for different repair attempts.

A later extension is to model distributions and releases as RDF resources rather
than storing only their names and versions as literals. A repair attempt could
then link to the selected distribution, release, and verified import evidence.
This would make it easier to ask cross-run questions, such as which notebooks
were repaired with the same package version, while preserving the attempt-level
provenance already recorded by the pipeline.

\section{Widening Repair Coverage Safely}
\label{sec:fw-coverage}

The live-PyPI evaluation ended with 52 abstentions among 187 notebooks
(\Cref{sec:v-final-abstention}). Abstention is a safety outcome, not simply a
missing repair: it means that the pipeline could not establish a sufficiently
verified action. Future coverage work should therefore preserve the current
rule that a distribution name and its import evidence must be verified before
Docker applies a repair.

The most promising improvement is to reduce dependence on the static
import-to-distribution mapping. A maintained external mapping source, combined
with the existing PyPI and wheel checks, could resolve more imports while
retaining the same safety boundary. It should be evaluated against a manually
checked sample before being allowed to change repair decisions. Extending a
local mapping table remains useful for well-understood cases, but it cannot be
the only long-term strategy because it needs continual maintenance.

Coverage is also limited by the kinds of repair the pipeline deliberately
excludes. A \texttt{wrong\_version} repair needs reliable compatibility evidence
and repository context (\Cref{sec:m-repair-compat}). The current pip-only scope
does not repair system libraries, local files, or an outdated import inside a
notebook. Future work could test additional repair actions, such as a
source-level import replacement, but each action needs its own evidence rule,
safe application procedure, and Docker-based validation. It should not be
treated as an unconstrained language-model edit.

The two-round limit is another deliberate boundary. The worked case in
\Cref{sec:m-worked-example} shows why a targeted repair can expose a later
dependency error. A controlled experiment with three or four rounds could
measure whether a larger budget yields more complete notebook recoveries or
only moves failures further into execution. Recording a Docker image digest and
an installed-package inventory for each original execution would make that
experiment more reproducible and would help distinguish a repair effect from
changes in an unpinned environment.

\section{Stronger Evaluation Designs}
\label{sec:fw-evaluation}

The current evaluation is intentionally transparent about its scope: each model
configuration and comparison condition was run once. Repeating the evaluation
with fixed package snapshots and repeated model calls would show how sensitive
the reported outcomes are to model sampling, Docker timing, and changing
external services. Reporting variation across runs would be more informative
than presenting a single run as a stable property of a model or method.

A focused ablation should test the contribution of PyPI grounding itself. The
PLLM-style comparison in \Cref{sec:v-pllm-comparison} compares two different
repair approaches, so it cannot isolate one component. A better ablation would
hold the input records, model, Docker component, repair-round limit, and frozen
package snapshot constant, then compare the thesis pipeline with and without
the grounding checks. The result should report both full notebook recovery and
targeted-error resolution, because these measures answer different questions.

\section{Extending the Human Evaluation}
\label{sec:fw-human}

The human evaluation is descriptive and uses a convenience sample of 15
participants. The blinded comparison found that resolver-informed templates
were rated more positively than the selected LLM explanations for the four
tested errors (\Cref{sec:v-human-eval-comparison}). This is a useful finding,
but it is not a general ranking of explanation methods.

A larger, pre-registered study could recruit readers with defined programming
experience, assign errors and explanation conditions using a balanced design,
and analyse ratings at the participant level. Expert review against the actual
root cause of each notebook would add a measure of objective correctness,
which the current perceived-correctness item cannot provide. The same study
could include explanations for newly exposed Round-2 errors and for both model
configurations; Chapter~6 currently evaluates those explanations only for
completion and schema validity (\Cref{sec:v-final-explanation}).

The existing free-text feedback also suggests a practical prompt experiment.
Several readers wanted more explanation of the likely cause and less repetition
of the error message. A revised prompt can be compared with the current one on
the same questionnaire items and error examples. The study should retain the
current distinction between explaining a failure and proposing a repair: a clear
explanation does not, by itself, make an unverified repair safe.
