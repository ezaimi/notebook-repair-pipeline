\chapter{Conclusion}
\label{chap:conclusion}

This thesis set out to close a specific, narrow gap: the existing FAIR
Jupyter reproducibility pipeline can detect that a notebook fails because of
a missing or incompatible Python package, but it does not explain that
failure or attempt to repair it. \Cref{chap:related-work} showed that the
individual pieces needed to close this gap -- failure detection, automated
dependency inference, and LLM-based program repair -- already existed
separately in the literature, but not combined inside a reproducibility
pipeline, grounded in live package data, and paired with a plain-language
explanation.

\Cref{chap:problem-dataset} through \Cref{chap:validation} reported what has
actually been built to close it. Of the 214 dependency-error notebooks in
the Docker pipeline's own residual failures, 200 fall inside this thesis's
pip-only repair scope. A deterministic classifier decides scope and subtype
before any language model is involved.

An explanation component is designed
to turn a raw error message into a plain-language, schema-validated
description of what went wrong, for every one of the 214 rows, not only the
repairable ones -- a scope confirmed in a real, committed example
(\Cref{sec:m-explanation-example}). It has since been run across all 200
repair-scope rows, producing a schema-valid explanation for 185 of the 187
final evaluation rows; it has not been run on the 14 rows that remain in
explanation scope but fall outside repair scope.

A repair component proposes a fix using an open, locally-run model whose
suggestion is checked, field by field, against live PyPI metadata and a
small, hand-curated compatibility registry, so that a suggested package name
or version is never a guess. A fix-application component applies that
proposal inside a rebuilt environment equivalent to the one the notebook
originally failed in, re-runs the whole notebook, and classifies the result
into exactly three outcomes. A result-logging component then joins the
classification, explanation, and repair records these four components
already produced into one persistent record per repair attempt, and a
knowledge-graph mapping re-expresses that record as RDF and links it to the
notebook it repairs inside the existing FAIR Jupyter knowledge graph. All of
this is implemented, covered by 332 automated tests.

It was additionally
checked against real PyPI, a real Ollama model, a real Docker daemon, real
GitHub repositories, and, for the logging and knowledge-graph components,
the real Morph-KGC mapping engine and the knowledge graph's own source data
-- first in a small pilot, and then, for the repair layer as a whole, in a
final evaluation over the complete 187-row evaluation split
(\Cref{chap:validation}).

Both the small pilot and the final evaluation produced the same finding,
worth restating here because it shapes how the rest of this project should
be read: a repair attempt that resolves its targeted dependency error often
uncovers a second, previously invisible one. This is not a weakness of the
components built for this thesis -- their own classification logic is
separately proven capable of reporting a completely clean result -- but a
real characteristic of research notebooks that depend on more than one
package. Across the final evaluation, 84.9\% of real repair attempts
resolved the error they targeted, and yet no notebook in the 187-row split
reached complete recovery within the two-round repair budget: the
recurring cause was not a bad repair, but a second dependency error the
first repair had simply not reached yet, together with a package-mapping
coverage gap (\texttt{mapping\_unknown}) that kept the repair agent from
even reaching the language model for the majority of its 235 invocations
across both rounds.

It is also a direct argument for the
two-round repair mode, which has since been built, small-pilot-validated,
and exercised at full evaluation scale (\Cref{chap:future-work,chap:validation}):
a single repair attempt is often only the first of several a real notebook
may need. In the final evaluation, Round 2 fired for 48 notebooks but fixed
none of them beyond what Round 1 already had, chiefly because 36 of those
48 abstained again on the same package-mapping gap. Whether a larger repair
budget, or better mapping coverage, would change this outcome is still an
open, unmeasured question.

Several design decisions changed along the way, and \Cref{chap:methodology}
recorded each one rather than hiding it behind a description that only
matches the final result. The clearest examples are that the original
containers this system was assumed to reuse for fix validation turned out
never to have been preserved, so the environment is rebuilt from the same
recipe instead; that the repair proposal's own persisted record does not
carry a notebook's identity forward, so a re-join step had to be added; and
that the explanation component's output format changed from free prose to
strict, schema-validated JSON once it had to fit inside an automated
pipeline. A further open question from the original design -- whether the
Docker pipeline's own notebook and repository identifiers actually coincide
with the ones the existing FAIR Jupyter knowledge graph was built from --
was resolved only once it was checked directly against that graph's own
source data, rather than assumed, confirming that the two agree on all 214
records inspected and that no separate crosswalk table is needed to link a
repair attempt to its notebook. None of these changes weaken the system --
each was made because a concrete implementation problem or a genuine open
question required it, and each is now covered by a regression test or a
recorded check.

An orchestrator connects the existing
components -- result logging and knowledge-graph enrichment, and the
bounded two-round repair mode, included -- without a person
driving each attempt by hand, and has run unattended over the complete
187-row evaluation split. Abstaining rather than guessing an unsupported
package name, and correctly reporting \texttt{still\_failing} on a genuinely
new error rather than claiming a repair that did not happen, are the
conservative behaviours this thesis deliberately built into the system, and
the final evaluation shows both working as intended, at a scale a small
pilot could not have shown. What remains, as \Cref{chap:future-work}
states, is enriching the knowledge graph at the same full-evaluation scale,
and the explanation-quality and baseline comparisons that were always
planned as follow-on work. None of this requires redesigning any of the
components described in this thesis; it extends work that is already
built, tested, and now evaluated.
