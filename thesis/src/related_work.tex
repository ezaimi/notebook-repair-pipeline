\chapter{Background and Related Work}
\label{chap:related-work}

This chapter reviews the prior work relevant to this thesis and positions the
thesis contribution in relation to it. It covers four areas: measuring notebook
reproducibility, automatically restoring executability, using large language
models (LLMs) for dependency resolution and program repair, and applying FAIR
data principles to record repair outcomes in a knowledge graph. The chapter
then identifies the gap that remains when these approaches are considered
together.

\section{Reproducibility of Computational Notebooks}
\label{sec:rw-reproducibility}

Computational reproducibility means that a published analysis can be
re-executed by someone else and produce the same result. For a Jupyter
notebook, the weaker and more basic question is whether it can be
\emph{re-executed at all}: does the code still run, independent of whether
the numbers come out identical. This thesis targets that weaker property,
re-executability, as the necessary first step before reproducibility in the
fuller sense can even be discussed.

A large-scale study by Pimentel et al.~\cite{pimentel2019msr} measured
this directly. Out of 1.4~million notebooks collected from GitHub, only 24.11\% of
the notebooks they attempted ran without an error, and only 4.03\% produced
results matching those already stored in the notebook. Samuel and
Mietchen~\cite{samuel2024gigascience} studied notebooks linked from
biomedical publications on PubMed Central. Of the 10,388 notebooks whose
dependencies could be installed and which were re-executed, 1,203 (11.6\%)
ran without an error. Of these, 879 notebooks (8.5\% of all re-executed
notebooks) produced results identical to those stored in the original
notebook. The working dataset used in this thesis is described separately in
\Cref{chap:problem-dataset}. It is a smaller residual dataset produced by the
newer Docker-based FAIR Jupyter pipeline.

The dependency focus of this thesis follows the detailed error analysis in
that FAIR Jupyter study. It recorded 6,588 \texttt{ModuleNotFoundError} and
\texttt{ImportError} exceptions among the re-execution attempts. The
local snapshot reported in \Cref{sec:pd-l1} has a slightly different count
because it applies a different counting rule: it excludes skipped and
environment-installation failures before counting dependency exceptions. The
two figures must therefore not be compared as if they used the same
denominator. Together, they motivate the focus on missing and incompatible
Python dependencies, without implying that every notebook failure has the
same cause.

Detecting these failures is itself useful. Samuel and
K{\"o}nig-Ries~\cite{samuel2020reproducemegit} built ReproduceMeGit, a
visualisation tool that runs the notebooks in a GitHub repository and shows,
for each one, whether it succeeded, crashed, or produced different output
than before. Tools like this make the scale of the problem visible to a
repository owner, but they stop at reporting: they do not explain a failure
in terms a non-programmer can act on, and they do not attempt to fix
anything.

\section{Restoring Executability}
\label{sec:rw-restoring}

A separate line of work tries to go one step further and automatically
restore a broken environment rather than only reporting that it is broken.

\subsection{Environment Capture and Large-Scale Re-execution}

Several established tools aim to preserve or reconstruct the software
environment needed to run research code. repo2docker~\cite{forde2018repo2docker}
reads the configuration files in a repository and builds a container image.
Binder~\cite{jupyter2018binder} uses such an image to let people run the
repository interactively in a web browser.

Other tools capture an environment that has already worked. ReproZip~\cite{rampin2016reprozip}
observes a program on the author's machine and packages the files, software,
and dependencies used during that run. Code Ocean~\cite{cheifet2021codeocean}
packages code, data, and dependencies together in an executable capsule.
In short, these tools try to make a known environment available again.

The repair pipeline in this thesis starts at a later point. A notebook has
already been run in a reconstructed environment, but it still stops with a
dependency error. The pipeline uses the recorded error and package information
to derive a focused repair, such as installing a missing package, or to abstain
when the available evidence is insufficient. It then re-executes the complete
notebook to check whether an approved repair helped.

Trisovic et al.~\cite{trisovic2022execution} are a close methodological
comparison. They re-executed R research code at scale in controlled Docker
environments and recorded whether each run succeeded, failed with an error,
or exceeded a time limit. They also measured the effect of basic automatic
code cleaning. Their study measures and classifies execution outcomes. This
thesis instead evaluates repairs for a defined subset of Python notebook
dependency failures.

\subsection{Static Analysis and Knowledge Graphs}

Wang et al.~\cite{wang2020ase} studied how execution environments could
be reconstructed by analysing a notebook's own code. They followed this
with SnifferDog~\cite{wang2021snifferdog}, a tool that statically
inspects a notebook's imports and matches them against a database of
known package APIs. SnifferDog correctly inferred the required
environment for 92.6\% of the notebooks it was tested on. This result
makes an important point that motivates the present thesis: a notebook
that looks broken is often not broken in its logic at all. It simply
lacks the right dependency information, which can in many cases be
recovered automatically.

A separate family of tools builds this dependency knowledge as an explicit
knowledge graph rather than analysing one notebook at a time. Horton and
Parnin's DockerizeMe~\cite{horton2019dockerizeme} introduced this idea: it encodes
package-to-module mappings from Libraries.io in a graph database and uses it
to infer, and then containerise, the dependencies a Python snippet needs.
Ye et al.'s PyEGo~\cite{ye2022pyego} extended the same idea to a much larger
graph covering third-party packages, the Python interpreter version, and
system libraries together, reporting a 0.4--3.5$\times$ accuracy improvement
over DockerizeMe. Cheng et al. added explicit conflict detection between
transitive dependencies with PyCRE~\cite{cheng2022pycre}, and later refined
the approach with ReadPyE~\cite{cheng2024readpye}, which reached 79.75\%
successful environment reconstruction, the strongest result among the
knowledge-graph approaches reviewed here.

These knowledge-graph approaches share one structural limitation: they can
only recommend a package or version that is represented in their indexed
data. Such a graph must be maintained and updated as new PyPI releases
appear, and a package or release that has not yet been indexed is
unavailable to it until the graph is rebuilt. This limitation motivates
replacing a fixed package-and-version snapshot with a live query against
the package registry itself, which is the design this thesis adopts
(\Cref{chap:architecture}). The primary pipeline queries live PyPI package
information. A frozen PyPI evidence snapshot is used only for the matched
comparison with the PLLM-style baseline, so that both methods receive the
same package information.

\subsection{Open LLMs in the Repair Pipeline}
\label{sec:rw-llm-primer}

An LLM generates text from the context supplied to it. In this thesis, that
context contains dependency-repair information, such as an error message, a
failing import name, and available package evidence. The LLM does not run
commands or decide whether a repair succeeded; Docker re-execution makes that
decision.

An open-weight model makes its parameters available for local deployment,
subject to its licence. In contrast, a proprietary model is normally used
through a provider's external API and its parameters are not available to the
user. This thesis uses an open-weight model through Ollama, a local serving
runtime. The selected model and its hardware configuration are described in
\Cref{chap:methodology}.

Error messages alone can be difficult for readers to interpret
\cite{becker2019errormessages}. LLM-enhanced explanations have been studied as
one way to make such messages more interpretable and actionable
\cite{leinonen2023errormessages}; this thesis applies that idea to dependency
failures and keeps the explanation separate from the evidence-based repair
decision.

LLM output is not automatically reliable. A model can produce invalid JSON,
suggest a package that does not exist, or choose an unsuitable version. The
repair component therefore uses retrieval-augmented generation (RAG): it
restricts the model to information that can be checked against package
evidence. When the model chooses a version, it can choose only from an
already verified list of candidates. When it proposes a package for an import
that deterministic sources could not map, the proposed package must first be
verified against PyPI and wheel-import evidence. Otherwise, the pipeline
abstains.

Within this pipeline, the LLM has three roles. It explains a dependency error
in plain language, may propose one distribution name for a previously unmapped
import, and may choose between several verified version candidates. It never
installs a package directly. The retrieval, verification, and validation
procedure is described in \Cref{sec:m-repair-retrieval}.

\subsection{LLMs for Dependency Resolution}
\label{sec:rw-llm-dep}

Bartlett et al.'s PLLM~\cite{bartlett2025pllm} is the closest prior system
to this thesis and its main point of comparison. PLLM uses an LLM,
retrieval-augmented with live PyPI data, to resolve missing or incompatible
Python dependencies from execution feedback. Its published implementation
accepts a standalone Python file and constructs its own execution image. In
contrast, the separate repair pipeline developed in this thesis starts from
failures recorded for Jupyter notebooks and reconstructs a repository-specific
Docker environment. Both approaches use package information and execution
feedback to assess proposed dependency repairs. A direct execution of PLLM
would therefore not provide a like-for-like notebook comparison;
\Cref{sec:v-pllm-comparison} uses a notebook-adapted PLLM-style baseline
instead. The thesis pipeline also limits repair to two rounds, provides a
human-readable explanation, and records structured outcomes for
knowledge-graph export.

In their experiments, PLLM reported 218 (15.97\%) more fixes than ReadPyE and
281 (21.58\%) more fixes than PyEGo~\cite{bartlett2025pllm}. More broadly,
RAG grounds a model's output in retrieved information rather than relying only
on its training knowledge~\cite{lewis2020rag,gao2024ragsurvey,tao2025racg}.
This makes it a suitable pattern for package repair, where a proposed package
name or version must be checked against current package information.

Adjacent work also uses LLMs to reconstruct executable repository
environments. Installamatic searches repository documentation before generating
and testing an installation environment, ExecutionAgent prepares build and
test scripts for arbitrary projects, and Repo2Run records a successful
container-configuration process as a Dockerfile
\cite{milliken2024installamatic,bouzenia2025executionagent,hu2025repo2run}.
These systems show that environment reconstruction is an active research
problem. The present pipeline has a narrower purpose: it starts from a
recorded notebook dependency failure, restricts a repair to verified package
evidence, and validates that action by re-executing the notebook.

\subsection{LLM-Based Program Repair and Notebook-Specific Work}
\label{sec:rw-apr}

More broadly, LLM-based automated program repair (APR) is an active
field. Yang et al.'s survey~\cite{yang2025aprsurvey} organises 63
systems published between 2022 and 2025 into four design paradigms:
fine-tuning, prompting, procedural pipelines, and agentic frameworks.
Agentic frameworks, where the model plans and re-plans its own next
action, perform well on complex, multi-file bugs, but at a real cost in
latency and control. That trade-off directly motivates a design
decision explained in \Cref{chap:architecture}: this thesis structures
its repair layer as a fixed, procedural pipeline, not an autonomous
agent, because the target workload is hundreds of independent, mostly
single-dependency notebook failures processed in batch, not a small
number of complex interactive sessions. The same survey also confirms
that retrieval-augmented context improves repair quality across every
paradigm it studied, reinforcing the PyPI-grounding decision from
\Cref{sec:rw-llm-dep}.

Two lines of work are specific to notebooks. Grotov et
al.~\cite{grotov2024untangling} released a dataset of buggy notebooks,
together with a proposed agent design. They followed it
with a full implementation~\cite{grotov2024debug} that observes the
output of each execution attempt, decides what to change, applies it,
and tries again. That second paper establishes a point this thesis
relies on directly: because a notebook keeps state between cells, a
candidate fix can only be judged correct by re-running the
\emph{whole} notebook from the top, not just the cell that originally
failed (\Cref{chap:architecture} adopts this rule for the same reason).
Xia and Zhang's ChatRepair~\cite{xia2024chatrepair} similarly feeds
re-execution feedback back into the next repair attempt, in a
conversational loop, achieving 162 of 337 fixes on a general Python bug
benchmark. The same feedback principle underlies the bounded two-round
repair mode built for this thesis (\Cref{sec:orchestrator}), with one
difference: the budget here is fixed at two rounds rather than left open.
Reyes et
al.'s Byam~\cite{reyes2025byam} and Tang et al.'s
SynFix~\cite{tang2025synfix} both target dependency-aware repair
outside the notebook setting: breaking dependency updates in Java, and
structured cross-file repair, respectively. Both motivate giving the
repair process structured dependency context rather than the bare error
message. This thesis follows that principle in a different form. The repair
component uses the classified error and verified package evidence. It also
reads repository dependency declarations, such as \texttt{requirements.txt},
as contextual but non-authoritative evidence. A declaration can support or
conflict with a candidate, but it cannot prove that a distribution provides a
particular import; PyPI and wheel-import evidence remain the verification gate
(\Cref{sec:m-repair-retrieval}).

On the interactive side, Jupyter AI~\cite{jupyterai2023} lets a user ask an
LLM inside JupyterLab to explain an error or generate a fix. It is a useful
point of contrast: Jupyter AI is designed for one user working on one
notebook at a time and must be triggered manually after every failure. It
has no route into a batch reproducibility pipeline and no connection to the
structured metadata such a pipeline already records. The system built for
this thesis is designed for exactly the opposite situation: no user present,
hundreds of notebooks, and existing structured failure metadata to build on.

Model and prompt choice also draw on this literature. Szalontai et
al.~\cite{szalontai2024codellama} find that a smaller, code-specialised
model can outperform a larger general-purpose model on bug-fixing tasks.
A broader empirical study of LLM-based APR~\cite{empiricalapr2025} likewise
finds that code-specialised models tend to perform well on Python repair.
Dinh et al.'s comparison of prompting techniques for code
generation~\cite{dinh2024codeprompteval} informs the structured-output,
few-shot prompt design described in \Cref{chap:methodology}. Their finding
that declared package information can improve dependency-aware generation is
also relevant here. The pipeline reads repository dependency declarations as
context, while verified PyPI candidates constrain any package or version that
can be selected. The detailed prompt design is described in
\Cref{chap:methodology}.

\section{FAIR Principles and Knowledge Graphs}
\label{sec:rw-fair}

The FAIR Jupyter project provides the execution records and knowledge graph
that this thesis builds on. It is grounded in the FAIR principles: that data,
and by extension research software, should be Findable, Accessible,
Interoperable, and Reusable~\cite{wilkinson2016fair}. Barker et al.~\cite{barker2022fair4rs}
extend these principles specifically to research software. They argue
that the Reusable principle for software requires recording the
\emph{provenance} of its execution environment -- not only the code
itself, but the conditions under which it did or did not run. Samuel
and Mietchen's FAIR Jupyter knowledge
graph~\cite{samuel2024fairkg,samuel2024zenodo} already stores exactly
this kind of provenance for the original execution attempts. Recording
a repair attempt in the same graph, using the PROV
ontology~\cite{provenance2013} for the activity/agent/time structure,
extends that existing provenance record to cover repair as well as
detection. Other provenance approaches make complementary choices: ProvONE
extends PROV for scientific-workflow structure, noWorkflow captures
provenance directly from scripts, and RO-Crate packages research artefacts
with machine-readable metadata
\cite{provone2016,noworkflow2014,rocrate2022}. The repair mapping uses the
smaller PROV-O subset needed to record the evidence, decision, and outcome of
each repair attempt. This is the basis for objective O6, designed in
\Cref{chap:architecture}, implemented in \Cref{chap:methodology}, and
validated in \Cref{chap:validation} first on pilot data and then by locally
materialising the complete table of the final evaluation. That materialisation
is a validated run artefact, rather than a published or publicly queryable
repair graph.

\section{Research Gap}
\label{sec:rw-gap}

Taken together, the literature above shows that the individual building
blocks already exist separately. Pipelines exist that detect and record
reproducibility failures at
scale~\cite{samuel2025docker,samuel2024gigascience,samuel2024fairkg}. Tools
exist that infer or restore a missing Python
environment, from static analysis~\cite{wang2021snifferdog} to
knowledge graphs~\cite{horton2019dockerizeme,ye2022pyego,cheng2022pycre,cheng2024readpye}
to live-retrieval LLMs~\cite{bartlett2025pllm}. LLM agents exist that can fix
errors in notebooks specifically, interactively, one session at a
time~\cite{grotov2024untangling,grotov2024debug}. FAIR-aligned provenance
recording exists for the original failures~\cite{samuel2024fairkg}.

Among the systems reviewed for this thesis, none combines all of the
following: (1) an evidence-grounded repair layer with limited LLM roles that
runs autonomously, without a user manually triggering each attempt; (2) a
separate, repository-aware notebook repair pipeline fed by failures recorded
in a reproducibility pipeline; (3) repair suggestions grounded in PyPI data
for pip-based dependency errors; and (4) a plain-language explanation together
with an RDF export designed to interoperate with the FAIR Jupyter knowledge
graph.

PLLM~\cite{bartlett2025pllm} is the closest system in mechanism, but it was
not designed for repository-based notebook failures and does not provide the
explanation or knowledge-graph export added here. Grotov et al.'s agents~\cite{grotov2024untangling,
grotov2024debug} are the closest for notebooks specifically, but they assume
an interactive session with a live kernel, not an autonomous batch pass over
a pipeline's own residual failures. \Cref{tab:rw-gap} summarises this
positioning against the thesis objectives introduced in
\Cref{chap:introduction}.

\section{Requirements Derived from the Research Gap}
\label{sec:rw-requirements}

reproducibility pipelines record failures but do not derive a repair decision;
interactive notebook agents require a user; and LLM-based repair systems need
evidence and execution-based validation. \Cref{tab:rw-requirements} makes
these requirements explicit and states how each one is checked in this thesis.
They are design and evaluation criteria, not claims that one earlier system
must satisfy every requirement.
