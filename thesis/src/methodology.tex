\chapter{Methodology and Implementation}
\label{chap:methodology}

\Cref{chap:architecture} defines the components of the repair workflow and
the information they exchange. This chapter explains how they were
implemented: the concrete rules, evidence sources, and validation steps
that turn a recorded dependency failure into either a repair attempt or an
explicit abstention.

Every classified error can receive a plain-language explanation, but only
third-party Python dependency errors within the pip-based scope reach repair
generation. The repair component creates and verifies PyPI distribution
candidates before a repair is proposed. The LLM can explain an error,
propose one additional distribution when deterministic resolution cannot
verify one, or choose from already verified version candidates. It does not
validate its own output: Docker re-execution decides whether an applied
repair worked. The sections follow this data flow, from dataset preparation
to logging and RDF export; \Cref{sec:m-worked-example} later traces one
real record through the complete workflow.

\section{Implementation Overview}
\label{sec:m-overview}

This section gives a compact view of the implemented workflow before the
following sections describe each stage in detail.

\begin{verbatim}
Docker-pipeline dependency-error dataset (214 rows)
  -> dataset preparation      scripts/prepare_dependency_dataset.py
  -> context extraction /
     classification           scripts/extract_error_contexts.py
  -> LLMExplainer             scripts/run_llm_explainer.py
  -> repair eligibility check
  -> distribution candidates: aliases, identity/PEP 503,
     and a public mapping source
  -> PyPI and wheel verification
  -> RAGRepairAgent           scripts/rag_repair_agent.py
  -> FixApplicator            scripts/fix_applicator.py
  -> new error: reclassify, explain,
     repair if eligible (round 2)  scripts/run_pipeline.py
  -> ResultLogger (SQLite)    scripts/result_logger.py
  -> CSV export               scripts/export_repair_attempts_csv.py
  -> RML mapping (Morph-KGC)  repair_attempts.rml.ttl
  -> repair RDF linked to FAIR Jupyter KG notebook IRIs
\end{verbatim}

The candidate-generation steps are deterministic. A candidate becomes
eligible for repair only when PyPI confirms that the distribution exists and
wheel evidence confirms that it provides the requested import. A dependency
declaration such as \texttt{requirements.txt}, when available, is recorded
as context but does not prove this import--distribution relationship. The
LLM is used only after these checks: it may propose one additional
distribution if none has been verified, or select from verified version
candidates for a wrong-version error. Every proposed repair then passes the
same validation before FixApplicator runs it.

The normal workflow uses live PyPI evidence. A frozen snapshot is used only
for the matched PLLM-style comparison in \Cref{chap:validation}. Each stage
can run separately for development and testing, while
\texttt{scripts/run\_pipeline.py} also drives the full workflow in one
unattended pass.

\section{Dataset Preparation}
\label{sec:m-dataset}

The working dataset contains 214 dependency-error records from the Docker
pipeline: 200 are within the pip-based repair scope and 14 are excluded.
The 200 repair-eligible records are divided into a 13-record development
split and a 187-record evaluation split. This section explains how
\texttt{scripts/prepare\_dependency\_dataset.py} creates these records and
their labels.

The script reads the upstream \texttt{notebook\_executions} table and keeps
rows whose \texttt{error\_category} is \texttt{DEPENDENCY\_ERROR}. It assigns
two deterministic labels to every retained row:

\begin{itemize}
  \item a \emph{subtype}: \texttt{missing\_package},
        \texttt{wrong\_version}, \texttt{system\_library}, or
        \texttt{mapping\_unknown}; and
  \item a \emph{scope status}: \texttt{usable} for a pip-based repair or
        \texttt{excluded} when automated pip repair is not appropriate.
\end{itemize}

The rules use the recorded error type, error message, and extracted failing
module. A message mentioning a shared object file, for example, is labelled
\texttt{system\_library} and excluded because it requires system-level work
rather than a Python package installation. Known ambiguous names such as
\texttt{utils}, \texttt{statistics}, \texttt{config}, \texttt{helpers}, and
\texttt{src} are labelled \texttt{mapping\_unknown} and excluded because they
may refer to local repository code rather than a PyPI distribution.

This exclusion does not mean that every unfamiliar third-party import is
discarded. It is limited to imports that are ambiguous or likely local. Other
repair-eligible imports continue to the resolver described in
\Cref{sec:m-repair}, where deterministic sources and, if necessary, a
verified LLM-proposed candidate can be considered.

The scope decision is made before any LLM call so that repair eligibility is
auditable and reproducible. All records, including excluded ones, continue
to context extraction and explanation; the scope status determines only
whether automatic pip repair may be attempted.

The script writes a classified CSV file, a schema document, a statistics
file, and a split manifest. The manifest records the exact execution IDs in
each split. The development records are used for implementation checks and
prompt examples; evaluation-set records are not included as few-shot prompt
examples.

\section{Context Extraction and Classification Refinement}
\label{sec:m-classification}

After dataset preparation, \texttt{scripts/extract\_error\_contexts.py}
enriches every record with a refined subtype, a rule-based confidence level,
and best-effort source context. It does not change the repair scope decided
in \Cref{sec:m-dataset}: the fields \texttt{scope\_status},
\texttt{exclusion\_reason}, and \texttt{split} are carried forward
unchanged. Excluded records are also enriched because they still receive an
explanation.

\subsection{Root-Cause Hints}

The initial subtype is refined into a root-cause hint that helps the
explanation and repair components interpret the recorded error. The possible
hints are:

\begin{itemize}
  \item \texttt{direct\_missing\_package}: the requested import is absent
        from the execution environment;
  \item \texttt{import\_distribution\_name\_mismatch}: the Python import
        may differ from the PyPI distribution, such as \texttt{sklearn} and
        \texttt{scikit-learn};
  \item \texttt{version\_or\_api\_incompatibility}: a
        \texttt{cannot import name} failure;
  \item \texttt{transitive\_dependency}: a generic \texttt{ImportError};
  \item \texttt{system\_level\_dependency}: a missing shared library;
  \item \texttt{local\_import\_or\_path\_issue}: a likely local or ambiguous
        import; and
  \item \texttt{insufficient\_context}: too little information to classify
        the failure confidently.
\end{itemize}

The confidence value describes the reliability of this rule-based hint, not
the quality of the later LLM explanation. Direct patterns such as
\texttt{ModuleNotFoundError}, \texttt{cannot import name}, and shared-object
failures receive high confidence. Softer messages such as ``install'' or
``required'' receive medium confidence. Ambiguous local names and incomplete
error messages receive low confidence.

\subsection{Source Context for Explanations}

The error message alone does not always show why a notebook failed. The
context-extraction step therefore collects any available information that can
help LLMExplainer describe the error more clearly. This may include the
failing notebook cell, nearby import statements, and dependency declarations
from the repository.

The preferred source is the repository version recorded for the failed
execution. When that version cannot be retrieved, the script may use the
current \texttt{main} or \texttt{master} branch as additional context. This
fallback can help explain the error, but it is not treated as proof that the
retrieved code is identical to the code that originally failed.

If repository source is unavailable, the pipeline still creates an
explanation from the Docker pipeline metadata: the error type, error message,
failing module, subtype, and recorded cell index. A matching legacy execution
trace may also be retained as supporting context. It is used only when its
final error matches the current error exactly.

Repository dependency declarations, such as \texttt{requirements.txt}, are
also retained as context. They can later show whether a proposed version is
compatible with the repository declaration. They do not prove that a PyPI
distribution provides a particular Python import; that relationship is
verified later using PyPI and wheel evidence.

\subsection{Limitations}

Source context is collected on a best-effort basis. A repository branch may
have changed since the original failed execution, and a notebook cell index
may no longer refer to the same cell in a newer version of that notebook.
For this reason, remotely retrieved source is used to support an explanation,
not to replace the original Docker error record.

If context extraction fails for a record, the pipeline does not stop the
complete run. Instead, it stores a metadata-only context and makes the
missing source information visible in the explanation record. This preserves
the original error while avoiding unsupported assumptions about its cause.

\section{LLM Explanation Component}
\label{sec:m-explanation}

LLMExplainer (\Cref{subsec:llmexplainer}) produces a short, plain-language
explanation of each classified dependency failure. Its purpose is to help a
researcher understand what went wrong. It does not choose a package, select
a version, construct an installation command, or decide whether a repair
worked. Those tasks belong to the repair and validation components described
later in this chapter.

\subsection{Role and Separation from Repair}
\label{sec:m-explanation-role}

LLMExplainer has one task: explain the failure in plain, non-technical
language using only the supplied information. Its prompt explicitly forbids
repair recommendations. RAGRepairAgent generates repair proposals instead
(\Cref{sec:m-repair}). Keeping these tasks separate is important because a
repair proposal must be verified before FixApplicator applies it and Docker
re-executes the notebook.

Explanation is available for more errors than automatic repair. The pip-only
scope in \Cref{sec:pd-scope} decides which rows may be \emph{repaired}, not
which rows may be \emph{explained} (\Cref{sec:pd-explanation-scope}). For
example, a missing system library is outside the repair scope, but the
researcher still receives an explanation of the failure.

The same rule applies in Round~2. If a repaired notebook exposes a new error,
the pipeline classifies and explains that error before deciding whether it is
eligible for repair. The explainer uses the same prompt, schema, and retry
rule in both rounds; only the error record changes
(\Cref{sec:m-orchestrator-round2}).

\subsection{Model and Runtime Selection}

The primary configuration uses the open \textbf{Gemma 2 9B} model
(\texttt{gemma2:9b})~\cite{gemmateam2024}. It was selected because it is used in closely related
dependency-repair work, including PLLM~\cite{bartlett2025pllm}, and can run
locally on the available machine. Ollama serves the quantised model locally,
without a separate GPU-serving setup~\cite{ollama}. This suits a pipeline that processes
one notebook error at a time.

A separate model-sensitivity run uses Qwen through the same provider interface,
prompt, and output schema~\cite{qwenteam2025}. Its configuration and results are reported in
\Cref{sec:v-model-sensitivity}.

\subsection{Structured Explanation Output}
\label{sec:m-explanation-deviation}

An explanation must be readable for a researcher and usable by the pipeline.
For this reason, LLMExplainer returns one JSON object that is checked against
a fixed schema (\texttt{schemas/}\allowbreak\texttt{explanation.schema.json}).
It contains exactly six fields:

\begin{itemize}
  \item \texttt{summary} -- a short, plain-language statement of what failed;
  \item \texttt{root\_cause} -- why it failed, in the same plain language;
  \item \texttt{evidence} -- a list of the concrete signals the explanation
        is grounded in (the error type, the error message, the root-cause
        hint);
  \item \texttt{failing\_module} -- the module named in the explanation;
  \item \texttt{explanation\_confidence} -- \texttt{high}, \texttt{medium},
        or \texttt{low}; and
  \item \texttt{limitations} -- what the explanation could not determine,
        for example because only metadata, not source code, was available.
\end{itemize}

The \texttt{summary} and \texttt{root\_cause} fields are written for the
reader and remain short and non-technical. The other fields preserve the
evidence, uncertainty, and record identity needed by later pipeline stages.

The model's \texttt{explanation\_confidence} must not be confused with the
classifier's \texttt{confidence} (\Cref{sec:m-classification}). Classifier
confidence describes how clearly a rule matched the error. Explanation
confidence is the model's own assessment of its explanation. They can differ.
The latter is not a calibrated quality measure and is never used to accept an
explanation, rank explanations, or decide a repair. Its descriptive
relationship with participants' perceived-correctness ratings is reported in
\Cref{sec:v-human-eval-confidence}.

\subsection{Prompt, Validation, and Retry}

The prompt requires plain, non-technical language, permits only supplied
information, and forbids repair advice. The model may not invent a version,
file name, or cause. The runner sends the prompt to \texttt{gemma2:9b} through
Ollama, parses the reply as JSON, and checks it against the schema. Each
request has a 120-second timeout.

The retry rule is simple:

\begin{itemize}
  \item Invalid JSON or a schema violation receives one retry with validation
        feedback.
  \item A timeout or unavailable model receives one retry of the original
        request.
\end{itemize}

An unexpected runtime error is not retried. Any final failure is logged with
its category; the underlying dependency error remains in the dataset and an
independently eligible repair can still be considered. The evaluation reports
timeouts, unavailable models, and validation failures separately
(\Cref{chap:validation}).

Each result records the original error metadata, the model and prompt
configuration, and the generated explanation with its validation status,
latency, and retry count. This keeps source information separate from model
output and links the explanation to its notebook through
\texttt{notebook\_execution\_id}.

\Cref{tab:m-llm-configuration} records the model and serving parameters for
each component. The primary explanation and repair runs use the listed
Gemma/Ollama rows. No random seed is configured for either component. The
Qwen rows describe the separate model-sensitivity configuration.

\section{PyPI-Grounded Repair Generation}
\label{sec:m-repair}

RAGRepairAgent (\Cref{subsec:repairagent}) decides whether there is enough
evidence to attempt a repair. It does not install anything. Its output is a
structured decision that FixApplicator checks again before it constructs and
runs an installation command. The key distinction in this section is between a
\emph{candidate} distribution name and a \emph{verified} distribution: a name
becomes verified only after PyPI and wheel metadata show that it provides the
import the notebook requested.

\subsection{Overall Flow}

The repair process answers three questions in order: (1) what Python import is
missing or incompatible, (2) which distribution and versions are supported by
evidence, and (3) whether the selected repair actually works when the notebook
is run again. \Cref{fig:m-repair-flow} gives an overview. A “candidate” is only
a possible distribution name. It becomes a “verified distribution” only after
the PyPI and wheel checks succeed; only then can the pipeline consider a repair.

\subsection{Generating Distribution Candidates}
\label{sec:m-repair-retrieval}

The failing import is not automatically the name that \texttt{pip} must
install. For example, \texttt{sklearn} is provided by
\texttt{scikit-learn}, and \texttt{cv2} by \texttt{opencv-python}. The
resolver extracts the top-level import from the error. An error naming the
submodule \texttt{sklearn.\allowbreak model\_selection} therefore requests
the import \texttt{sklearn}.

For an eligible third-party import, the resolver creates distribution
candidates in the following order:

\begin{enumerate}
  \item an explicit mapping for genuine name mismatches;
  \item the same name as the import, normalised according to PEP~503
        \cite{pep503} so that
        upper case and the separators \texttt{.}, \texttt{\_}, and
        \texttt{-} are treated consistently; for example,
        \texttt{dms\_variants} becomes \texttt{dms-variants}; and
  \item a distribution suggested by the frozen public \texttt{pipreqs}
        tool~\cite{pipreqs}
        import-mapping snapshot.
\end{enumerate}

For example, the explicit mapping resolves the import \texttt{sklearn} to the
distribution \texttt{scikit-learn}.

These are candidate sources, not sources of truth. The resolver tries them in
order and records every attempt. It stops at the first candidate that passes
the verification described next. This lets common identity and normalised-name
cases proceed without adding a special entry to the local mapping file, while
retaining explicit mappings where names genuinely differ.

\subsection{Verifying a Distribution Candidate}

For each candidate, the resolver queries the official PyPI Simple API
\cite{pep691} and
checks that the distribution exists. It then removes releases that are
pre-releases, fully yanked, unparsable, or incompatible with the pipeline's
Python~3.10 runtime. Python~3.10 is fixed in
\texttt{config/\allowbreak rag\_repair.v2.yaml} because every repair attempt
uses the same \texttt{python:3.10-slim} Docker base image.

Existence on PyPI is not sufficient. A project with a similar name may not
provide the import that failed. The resolver therefore inspects an available
wheel without installing it. It reads the wheel's \texttt{top\_level.txt} or,
when that file is absent, its \texttt{RECORD} file. Only a wheel whose metadata
lists the requested top-level import verifies the candidate. For example, the
distribution \texttt{scikit-learn} is accepted for \texttt{sklearn} only when
wheel metadata provides \texttt{sklearn}.

If a deterministic candidate does not exist or does not provide the import,
the resolver continues to the next candidate source. If none passes, it records
the explicit \texttt{mapping\_unknown} status rather than an installation
command.

\subsection{Version Evidence for \texttt{wrong\_version} Errors}
\label{sec:m-repair-compat}

An \texttt{ImportError} can mean that a package is present but an expected
symbol is unavailable in its installed version. For this error type, the
resolver requires the recorded repository commit date. It retains only
Python-compatible, non-yanked releases that were already available on PyPI by
that date, then keeps at most the five newest of those releases. The same wheel
check confirms that each retained release provides the top-level import.

The date is evidence of what could have been installed when the repository
version was recorded. It does not prove the exact installed version or prove
that a nested symbol is available. If the commit date is unavailable, or no
safe release is found, the resolver reports an explicit abstention rather than
substituting a current latest version. Docker re-execution remains the final
test of a selected version.

\subsection{Repository Dependency Declarations as Context}
\label{sec:m-repair-nodeps}

After a distribution has been verified, the resolver reads the relevant
repository declaration, such as an entry in \texttt{requirements.txt}, when
one is available. It labels the relationship between the declaration and the
verified candidate as \texttt{absent}, \texttt{compatible}, \texttt{conflict},
or \texttt{unparsable}. This label is stored in the repair trace.

The declaration is useful context, but it does not prove that a distribution
provides an import and it cannot override PyPI or wheel evidence. A conflicting
pin is not silently replaced: it remains visible in the trace and may still be
tested, because that declared version could itself explain the observed error.
When the LLM is asked to select a version, this labelled declaration is included
in its prompt. FixApplicator also uses repository dependency files to rebuild
the baseline Docker environment, as described in \Cref{sec:m-fixapply-docker}.

\subsection{Choosing the Repair and the LLM's Role}

The decision policy uses deterministic actions when the evidence leaves no
choice. The LLM never writes a shell command or decides whether a repair
succeeded.

The model sees the classified error and only the evidence needed for its bounded

distribution proposed for an unresolved import is only a candidate: unless the
resolver verifies it, no repair is generated.


\subsection{Validation and Command Construction}

Every LLM response is checked against a JSON schema before it can affect a
repair. A proposed distribution must pass the same PyPI and wheel verification
as a deterministic candidate. A proposed version must be one of the verified,
date-anchored candidates. The validator also rejects an unknown action, a name
that differs from the verified distribution, and unsafe values such as shell
metacharacters or leading dashes. It never replaces a rejected value with a
guess.

Only after these checks does the pipeline construct an argument list. For
example, it constructs \texttt{python -m pip install scikit-learn} or
\texttt{python -m pip install scipy==1.13.1}. The LLM never produces an
executable command string. If an LLM response is invalid or unavailable, the
configured retry policy permits one further attempt; otherwise, the result is
an abstention.

\subsection{Runtime Configuration and Recorded Trace}

The primary repair configuration uses \texttt{gemma2:9b} through local Ollama,
with temperature 0.1, top-p 0.9, a 700-token limit, and a 300-second timeout.
The same configuration file limits PyPI requests to one every 0.5 seconds and
allows one retry after an HTTP~429 response. The separate Qwen sensitivity run
uses the same pipeline interface and is reported in \Cref{sec:v-model-sensitivity}.

Each repair record stores the requested import, scope decision, deterministic
candidate attempts, PyPI and wheel evidence, version candidates where relevant,
and the dependency-declaration label. It also records whether a decision was
deterministic, based on an LLM version selection, or based on an LLM distribution
proposal that later passed verification. A repair record with an applied action
contains the validated distribution, optional version, and constructed argument
list. FixApplicator uses the \texttt{notebook\_execution\_id} to recover the
repository and notebook information before it tests that action
(\Cref{sec:m-fixapply}).

\section{Fix Application and Notebook Re-execution}
\label{sec:m-fixapply}

FixApplicator answers the question RAGRepairAgent leaves open: \emph{does
the proposed repair actually work?} It contains no language-model call. It
is a deterministic component that applies an already-validated proposal,
re-runs the notebook, and classifies what happened. It follows five steps:

\begin{enumerate}
  \item recover the repository, notebook, and recorded commit from the
        classification record;
  \item independently validate the persisted repair fields and reconstruct
        the installation argument list;
  \item clone the repository, check out the recorded commit, and build a
        fresh Docker environment;
  \item install the validated repair and execute the target notebook from its
        first cell to its last cell; and
  \item record whether the notebook is fixed, still failing, or could not be
        tested reliably.
\end{enumerate}

The key point is that FixApplicator tests a proposed repair; it does not decide
which package or version should be repaired. The sections below explain each
step and the limits of this test.

\subsection{Recovering Notebook Identity}

\begin{sloppypar}
A RAGRepairAgent result is joined to the rest of the dataset by
\texttt{notebook\_execution\_id} alone; it carries no repository ID,
notebook name, or repository URL. FixApplicator therefore first looks up
each record's \texttt{notebook\_execution\_id} in the classification
dataset that accompanies the final evaluation
to recover this identity. If the ID is not found, or the matching record
lacks one of these fields, FixApplicator records the attempt as an
infrastructure failure (\texttt{apply\_error}, failure stage
\texttt{"join"}). Filling in a missing field with a default value could
silently clone or run the wrong repository, so no guess is made.
\end{sloppypar}

\subsection{Re-validating the Persisted Command}

FixApplicator does not execute the persisted \texttt{argv} as it is, even
though RAGRepairAgent already validated the proposal. It re-checks
\texttt{install\_name} and \texttt{version} with the same safety check
RAGRepairAgent uses, and rebuilds the argument list from scratch with the
same function. If the rebuilt list differs from the persisted one, the
record is rejected before anything runs. This catches a damaged or manually
changed result record before it reaches Docker. When the two lists agree,
FixApplicator uses the reconstructed list, not the persisted command text.

\subsection{Rebuilding the Docker Environment}
\label{sec:m-fixapply-docker}

The upstream Docker pipeline did not preserve its per-repository containers.
FixApplicator therefore cannot attach to the container in which the original
failure occurred. Instead, it creates a fresh disposable container for every
attempt. It uses the same base image (\texttt{python:3.10-slim}), the same
baseline dependency-installation procedure, and the same notebook command
(\texttt{jupyter nbconvert --to notebook --execute --allow-errors}) as the
reference Docker pipeline.

After the repository has been checked out, the baseline installation reads the
repository-root \texttt{requirements.txt}, when it exists, one entry at a time.
An entry that fails is recorded in the container output and skipped, matching
the reference procedure. The configured \texttt{setup.py} locations are then
installed from the checked-out repository. These dependency files recreate the
baseline in which the repair is tested; they are not proof that a package is the
right repair (\Cref{sec:m-repair-nodeps}). The validated repair is installed
only after this baseline step.

The reconstructed environment is comparable to, but not an exact copy of, the
original one. The recorded commit fixes the notebook source and dependency-file
contents. However, the upstream data does not preserve the original Docker image
digest or a complete installed-package list. An unpinned dependency may therefore
resolve to a newer release from PyPI. This is why the test is described as a
re-execution under a controlled reconstruction, not a replay of the original
container.

Only the target notebook is executed, and it is always executed from the first
cell. A notebook can depend on state created by earlier cells, so executing only
the failing cell would not show whether the repair works. The Docker build context
is kept separate from the repository clone to avoid sending the full Git history
to Docker. The clone is mounted into the disposable container at run time, so the
notebook source itself is unchanged.

\subsection{Commit Pinning}

Each repair attempted in the final evaluation requires a recorded repository
commit. FixApplicator clones the repository and checks out that exact commit
before it builds the container. This prevents a repair from being tested against
the repository's current default branch, which may have changed since the
original failure was collected.

If a record has no stored commit, it is skipped and the reason is recorded. If
the commit cannot be checked out, the result is an \texttt{apply\_error} with
the failure stage \texttt{checkout}. In neither case does the pipeline silently
fall back to the current branch. The commit thus anchors the source code and
dependency files used by the repair test, although it cannot by itself recreate
packages that were originally installed without version pins.

\subsection{Fix Application Safety}

FixApplicator never executes raw model output or a persisted command string.
It rebuilds the repair as a fixed \texttt{python -m pip install} argument list
from the independently validated package name and optional version. Before this
list is inserted into the generated Docker entry-point script, every dynamic
token passes a second, stricter allowlist for safe shell words. Git and Docker
are invoked from the host as argument lists, not through \texttt{shell=True}.

If the repair installation fails inside the container, the entry-point script
stops immediately and the notebook is not executed. Running an unfixed notebook
would not test the proposed repair. Static tests also check that
\texttt{shell=True}, \texttt{os.system}, \texttt{eval}, and \texttt{exec} do
not occur in FixApplicator or its Docker runner.

\subsection{Outcome Classification}

Exactly three outcomes are possible, listed in \Cref{tab:m-outcomes}. They
match the contract fixed in \Cref{chap:architecture}; no fourth value is
introduced.

\begin{table}[htbp]
  \centering
  \begin{tabular}{|l|p{9.3cm}|}
    \hline
    \textbf{Outcome} & \textbf{Meaning} \\
    \hline
    \texttt{fixed} & The re-executed notebook contains no error output in any cell. \\
    \hline
    \texttt{still\_failing} & The fix installed and the notebook re-ran, but an error remains -- possibly the same error as before, possibly a different one further into the notebook. \\
    \hline
    \texttt{apply\_error} & The repair could not be tested reliably, for example because of a join, clone, checkout, Docker build, fix-installation, timeout, or output-notebook failure. This does not show that the repair itself was ineffective. \\
    \hline
  \end{tabular}
  \caption{FixApplicator outcome values.}
  \label{tab:m-outcomes}
\end{table}

A \texttt{still\_failing} result additionally records whether the new
error is the same as the original one. The check is conservative: the
error is marked as the same only when the exception type matches
\emph{and} the original failing module name still appears in the new
message. The check is designed to under-claim sameness rather than
over-claim it, so a fix that resolved the original problem and uncovered
a different one is not reported as having done nothing. This distinction
matters a great deal in practice, as \Cref{chap:validation} shows.

\begin{sloppypar}
A row whose proposal was \texttt{"none"}, or whose repair-agent result status
was not \texttt{"success"}, is not treated as an attempt. It is recorded with a
separate \texttt{status: "skipped"} field rather than a fourth outcome
value. This keeps the three-value contract intact while still separating
``nothing was attempted'' from ``an attempt was made and failed''.
\end{sloppypar}

\subsection{Why a Real Pilot Was Necessary}
\label{sec:m-fixapply-bugs}

The unit tests passed before the component was used with real Docker executions.
The first real pilot nevertheless exposed three environment-specific problems:
Docker output was decoded incorrectly, the generated entry-point script had
incompatible line endings, and cleanup failed for some read-only files created
by \texttt{git clone} on Windows. Each problem was fixed and covered by a
regression test.

This is why the evaluation includes real Docker executions as well as automated
tests. Mocked tests can check the internal logic, but they cannot fully reproduce
the interaction between Docker, Git, the operating system, and subprocesses.


\subsection{Environment Isolation and What Is Out of Scope}

Every attempt uses a freshly named work directory and container. Both are
removed afterwards, whether the attempt succeeded, failed, or timed out.
Docker may reuse a built image across attempts through its own build
cache; this is expected and does not break isolation. The guarantee that
matters is a fresh clone and a fresh container per attempt, not a fresh
image layer every time.

FixApplicator returns one self-contained result per attempt. It does not decide
whether a second round is needed and does not persist results to a database or
knowledge graph. Those responsibilities belong to the Orchestrator and
ResultLogger (\Cref{sec:m-resultlogger}). When the Orchestrator requests a
second round, FixApplicator rebuilds a fresh container and reapplies the already
validated first-round repair before applying the second-round repair. This keeps
the second test cumulative even though every attempt uses a fresh container.

\section{Orchestration and the Bounded Second Round}
\label{sec:m-orchestrator-round2}

The orchestrator, \texttt{scripts/run\_pipeline.py}, runs the components in
one unattended pass over a dataset split. Its control flow was defined in
\Cref{sec:orchestrator}. This section explains how the pipeline handles a
notebook that runs further after a repair but then fails on another error.

\subsection{Round 1 and the Round 2 Trigger}

Every record first receives a classification and an explanation. If it is
repair-eligible, RAGRepairAgent produces a repair decision and FixApplicator
decides whether that decision can be tested in Docker. These steps form
Round~1. All component records for one notebook share one run identifier.

A second \emph{repair} round is started only when all of the following hold:

\begin{enumerate}
  \item Round~1 applied a repair and the notebook returned
        \texttt{still\_failing};
  \item the re-executed notebook contains a new error type and message;
  \item that error does not match the conservative same-error check from
        \Cref{sec:m-fixapply}; and
  \item after reclassification, it is a repair-eligible dependency error with
        a supported subtype.
\end{enumerate}

The same-error check is a routing rule, not proof that two errors are
semantically different. It reports the error as the same only when both the
exception type matches and the original failing module still appears in the
new message. If either condition is absent, the pipeline treats the error as
newly exposed and classifies it again. This conservative rule avoids repeating
the same repair when the original dependency error is still visible.

\subsection{Reclassifying and Explaining a Newly Exposed Error}
\label{sec:m-orchestrator-round2-explain}

When Round~1 returns a non-matching error, the orchestrator creates a new
classification record for that error. It retains the notebook and repository
identity because the notebook is the same, but it has its own failing module,
subtype, scope status, and root-cause hint. The same classification rules used
for the original record are used again.

The new error is explained before the pipeline decides whether to repair it.
This keeps explanation scope wider than repair scope. For example, a newly
exposed \texttt{missing\_package} error can be explained and repaired. A
\texttt{system\_library}, \texttt{mapping\_unknown}, or non-dependency error
is still explained, but does not reach RAGRepairAgent or FixApplicator.

The explanation does not influence the repair decision. RAGRepairAgent receives
the classified record and its PyPI evidence, not the explanation text. Likewise,
an explanation failure does not stop an otherwise eligible repair: a timeout or
model failure is recorded, and the repair path continues.

Two repair rounds are a hard limit (\texttt{MAX\_ROUNDS\_HARD\_CAP = 2}). This
limit bounds the cost of an unattended batch run; it does not show that two
rounds are sufficient for every notebook with a chain of dependency failures.
If the Round~2 re-execution exposes another error, that error is recorded in
the outcome, but it is not classified, explained, or repaired further.

\subsection{Why Round 2 Reapplies Round 1's Fix}
\label{sec:m-fixapply-round2}

Each repair attempt uses a fresh container, so the Round~1 container no longer
exists when Round~2 begins. Applying only the Round~2 fix in a fresh container
would test \emph{baseline environment + Round~2 fix}. It would not show whether
the two repairs together make the notebook run.

The orchestrator therefore reapplies the validated Round~1 installation before
it applies the Round~2 installation. The Round~2 notebook execution tests
\emph{baseline environment + Round~1 fix + Round~2 fix}. The test remains
isolated because these installations occur inside a newly created container;
no container state is carried forward from Round~1.

\subsection{What Is Recorded}
\label{sec:m-orchestrator-record}

The orchestrator produces two complementary records. The first is a per-notebook
JSONL trace. It stores the original classification and explanation, the Round~1
repair result, and the decision about Round~2. When an error is newly exposed,
the trace also stores its reclassification and explanation. This information is
retained even when that error is outside the repair scope.

The second record is the \texttt{repair\_attempts} table, written through
ResultLogger (\Cref{sec:m-resultlogger}). Every original record has one row:
an eligible record has a RAGRepairAgent result, while an excluded record is
represented by a recorded abstention. A repair-eligible Round~2 record receives
its own row. A newly exposed error that is explained but not repair-eligible has
no Round~2 table row; its explanation remains in the JSONL trace only.

Each table row stores the error context, explanation, repair decision, PyPI and
dependency-declaration evidence, validation outcome, model information, round,
and run identifier. Thus, the trace shows the complete control flow for one
notebook, while the table supports analysis across all repair decisions.

\section{Result Logging and Knowledge-Graph Enrichment}
\label{sec:m-resultlogger}

ResultLogger does not classify an error, generate an explanation, select a
repair, or run Docker. Its role is to turn the outputs of those stages into a
durable record that can be analysed later. It writes the
\texttt{repair\_attempts} table in SQLite and exports that table for the
knowledge-graph mapping. The implementation is in
\path{scripts/result_logger.py}; the export and mapping are implemented in
\path{scripts/export_repair_attempts_csv.py} and
\path{mapping/rml_mapping/repair_attempts.rml.ttl}.

\subsection{One Row for Each Repair Decision}
\label{sec:m-resultlogger-join}

The table has one row for every recorded repair decision. An original
notebook record always contributes one row: an eligible error contributes
the repair decision made by RAGRepairAgent, while an error outside the repair
scope is recorded as an abstention. If Round~1 exposes another dependency
error, Round~2 contributes a second row only when that new error is also
eligible for repair. A newly exposed error that is explained but outside the
repair scope remains in the JSONL trace, because no repair decision was made
for it.

ResultLogger combines four inputs: the error classification, the LLM
explanation, the repair decision, and the Docker validation result. The
classification and explanation are associated with the notebook execution
identifier. The validation result is associated with the exact repair
decision that Docker processed. When the stages are run separately, the
retained proposal position distinguishes repeated attempts for the same
notebook; when the orchestrator runs the pipeline, it passes the associated
records directly. A missing classification record is treated as an error
rather than silently creating an incomplete provenance row.

\subsection{What One Row Contains}
\label{sec:m-resultlogger-row}

The table has a SQLite primary key, \texttt{id}, and nineteen recorded
fields. They are grouped below by the question they answer. This grouping is
also a practical guide for reading one repair attempt.

\begin{table}[htbp]
\centering
\small
\caption{Information recorded for one repair attempt.}
\label{tab:m-repair-attempt-fields}
\begin{tabular}{p{0.29\textwidth}p{0.62\textwidth}}
\hline
\textbf{Question} & \textbf{Recorded fields} \\
\hline
What failed? & \texttt{notebook\_execution\_id}, \texttt{failing\_module}, and \texttt{subtype}. \\
What was explained? & \texttt{explanation}, \texttt{llm\_model}, and \texttt{prompt\_strategy}. \\
What repair was selected? & \texttt{action}, \texttt{install\_name}, \texttt{version}, \texttt{command}, and \texttt{rationale}. \\
What evidence supported it? & \texttt{pypi\_evidence} and \texttt{declared\_constraint}. \\

\hline
\end{tabular}
\end{table}

The fields describing the repair and the outcome have different sources.
The repair decision supplies its rationale. When Docker was invoked, its
record supplies the action actually applied and the observed outcome. For an
abstention, no Docker result exists, so the decision itself supplies the
recorded action and rationale; the outcome and post-repair-error fields are
left \texttt{NULL}. The shared \texttt{run\_id}, round number, and creation
time identify when the attempt was made.

\subsection{Preserving Structured Evidence}
\label{sec:m-resultlogger-json}

Some evidence cannot be represented honestly by one short value. The
\texttt{explanation} field therefore preserves the validated explanation
object, including its summary, root cause, evidence, confidence, and
limitations, rather than only its summary. The \texttt{pypi\_evidence} field
preserves the resolver result: the distribution candidates considered, the
wheel evidence, the safe version candidates where relevant, and warnings.
The separate \texttt{declared\_constraint} field records what a project
dependency declaration, such as \texttt{requirements.txt}, said about the
selected distribution and whether it was compatible, conflicting, absent, or
could not be parsed.

These values are stored as JSON text so that later analysis can inspect the
evidence behind a decision without reconstructing it from transient stage
files. A field is \texttt{NULL} only when its upstream stage produced no
value; it is not replaced by an empty string or an empty JSON object. This
distinguishes missing evidence from evidence that was actually observed.

\subsection{From SQLite to CSV}
\label{sec:m-resultlogger-csv}

SQLite remains the store of record for evaluation and provenance. The
exporter adds a CSV because the FAIR Jupyter mappings use CSV logical
sources in Morph-KGC~\cite{arenas2024morphkgc}, rather than a live SQLite connection. The CSV is an
exact export for the mapping; SQLite remains the operational store.

The table stores \texttt{notebook\_execution\_id}, while the knowledge graph
uses \texttt{notebook\_id}. During export, the script obtains the notebook
identifier from the classification data. If it cannot resolve an execution
identifier, it stops and names the affected table row instead of exporting a
repair attempt with no notebook link. The CSV contains \texttt{id} and
\texttt{notebook\_id}, followed by all nineteen stored fields unchanged.

\subsection{The RML Mapping}
\label{sec:m-resultlogger-rml}

The RML file has two maps over the exported CSV. RML expresses rules that map
heterogeneous structured data to RDF~\cite{dimou2014rml}. The first map creates one
resource for each repair attempt:
\url{https://w3id.org/reproduceme/repairattempt_{id}}. It is typed as both
\texttt{repr:RepairAttempt} and \texttt{prov:Activity}. The fields below are
then attached as literal properties. The mapping follows the vocabulary
strategy in \Cref{subsec:kg}: it reuses an existing term where possible and
uses a \texttt{repr:} term where a repair-specific property is needed.

\begin{center}
\small
\begin{tabular}{ll@{\hspace{0.6cm}}ll}
\texttt{failing\_module} & \texttt{repr:failingModule} &
  \texttt{pypi\_evidence} & \texttt{repr:pypiEvidence} \\
\texttt{subtype} & \texttt{repr:subtype} &
  \texttt{declared\_constraint} & \texttt{repr:declaredConstraint} \\
\texttt{explanation} & \texttt{repr:explanation} &
  \texttt{outcome} & \texttt{repr:fixOutcome} \\
\texttt{action} & \texttt{repr:fixAction} &
  \texttt{llm\_model} & \texttt{repr:llmModel} \\
\texttt{install\_name} & \texttt{repr:installName} &
  \texttt{prompt\_strategy} & \texttt{repr:promptStrategy} \\
\texttt{version} & \texttt{repr:fixVersion} &
  \texttt{round} & \texttt{repr:round} \\
\texttt{command} & \texttt{repr:fixCommand} & & \\
\texttt{rationale} & \texttt{repr:fixRationale} & \texttt{run\_id} & \texttt{repr:runId} \\
\end{tabular}
\end{center}

The post-repair error type and message reuse \texttt{repr:exception} and
\texttt{repr:msg}, respectively. They describe an error observed after a
repair attempt, not the original notebook error. The creation time maps to
\texttt{prov:endedAtTime} as an \texttt{xsd:dateTime}. Empty CSV fields
produce no RDF triple, which avoids representing unavailable evidence as an
empty observed value.

The second map links the repair attempt to its existing notebook resource
with \texttt{repr:hadRepairAttempt}. It uses the same notebook IRI pattern as
the existing notebook mapping, so no change to that mapping is necessary.
When Morph-KGC processes the CSV and RML file, it materialises RDF from these
records. This provides a structured export for the FAIR knowledge graph; it
does not by itself mean that the graph has been published or made available
through a query service.

\label{sec:m-resultlogger-identity}
The direct link is possible because the Docker pipeline and the existing FAIR
Jupyter knowledge graph use the same \texttt{notebook} and
\texttt{repository} primary keys for this dataset (\Cref{sec:v-i6}). A
separate crosswalk table is therefore not required.

\section{A Worked Example: One Record Through the Pipeline}
\label{sec:m-worked-example}

This section follows one evaluation-split record through the complete
workflow. It is included to make the data flow concrete, not to estimate the
pipeline's overall success rate. The record is
\texttt{notebook\_execution\_id}~198 from the repository
\texttt{VisualNeuroscience-UH/CxSystem2}. It is the same record used in the
introduction and architecture chapter, and it was not used as a few-shot
prompt example.

\noindent\begin{minipage}{\textwidth}
\medskip
\noindent\textbf{Step 1: Identify the failing dependency.}
The notebook \texttt{01\_basic\_use.ipynb}
fails with \texttt{ImportError: cannot import name
'VisibleDeprecationWarning' from 'numpy'}. Classification identifies
\texttt{numpy} as the failing module and labels the error
\texttt{wrong\_version}/\texttt{usable}. In plain terms, the notebook expects
a NumPy name that is unavailable in the environment used for the original
execution, so testing an earlier supported NumPy version is within the repair
scope.
\end{minipage}

\medskip
\noindent\textbf{Step 2: Explain the error.}
LLMExplainer produces a schema-valid explanation on its first attempt. It
states that \texttt{VisibleDeprecationWarning} is unavailable from the
installed NumPy API and that a version incompatibility is the likely cause.
Its confidence is \texttt{medium}, because the error message does not reveal
the installed NumPy version. The explanation helps the reader understand the
failure; it is not treated as proof of which version should be installed.

\medskip
\noindent\textbf{Step 3: Create a safe list of version candidates.}
The requested import and PyPI distribution have the same name:
\texttt{numpy}. The resolver confirms this distribution and verifies the
top-level \texttt{numpy} import in wheel metadata. It then retains five
Python~3.10-compatible, non-yanked releases that were available by the
recorded repository date: \texttt{1.24.1}, \texttt{1.24.0},
\texttt{1.23.5}, \texttt{1.23.4}, and \texttt{1.23.3}. This proves that the
candidate distributions provide \texttt{numpy}; it does not by itself prove
that every older NumPy symbol is available. Docker re-execution is the final
test of the selected version.

\medskip
\noindent\textbf{Step 4: Use the project declaration and select the repair.}
The repository's \texttt{requirements.txt} declares
\texttt{numpy >= 1.16.5}. All five verified candidates are compatible with
that declaration, so the constraint is recorded as compatible. The LLM is
given this evidence and selects the newest candidate, \texttt{numpy==1.24.1},
with the action \texttt{pin\_version}. Schema and grounding validation accept
the response. The pipeline then constructs the command deterministically:
\texttt{python -m pip install numpy==1.24.1}. The LLM selects from the
verified list; it does not send a free-form command to Docker.

\medskip
\noindent\textbf{Step 5: Apply the repair and re-execute the notebook.}
FixApplicator checks out the recorded repository version, rebuilds the
repository's Docker environment, applies the validated pin, and executes the
notebook from top to bottom. The installation succeeds and the notebook
execution completes successfully.

\medskip
\noindent\textbf{Step 6: Interpret the Docker result.}
The outcome is \texttt{fixed}: the original NumPy import error is absent and
the notebook completes without a new dependency error. This is both a
targeted-error resolution and a full notebook recovery, so Round~2 is not
needed.

\medskip
\noindent\textbf{Step 7: Record the trace.}
ResultLogger writes one repair-decision row for this notebook. It records the
original error context, the explanation, the compatible dependency
declaration, the selected NumPy pin, and the Docker outcome
\texttt{fixed}. As described in \Cref{sec:m-resultlogger}, the exported row
can be linked to \texttt{notebook\_id}~453 in the knowledge-graph mapping.

This example demonstrates the intended end-to-end behaviour: explain the
failure, select a repair from grounded evidence, test it in Docker, and
record a full recovery only when the notebook completes successfully.

      sources provide none, and choose among verified version candidates. All
      proposed choices must pass validation (\Cref{sec:m-repair}) &
      The LLM cannot freely invent a package, version, or shell command.
      Some uncertain cases therefore end in abstention. \\
    \hline
    Dependency declarations provide context, not unquestioned truth &
      Files such as \texttt{requirements.txt} help rebuild the repository
      baseline. Their relevant constraints are compared with a verified
      repair candidate and recorded (\Cref{sec:m-repair-nodeps}) &
      A declaration can be stale, incomplete, or itself incompatible. A
      conflict is made visible and logged; it is not silently overwritten. \\
    \hline
    Docker decides whether a repair worked &
      A validated proposal is applied in a fresh reconstruction of the
      recorded repository commit and tested by re-executing the notebook
      (\Cref{sec:m-fixapply}) &
      This is slower than judging a proposal from metadata alone, but it
      avoids treating an installation command as a successful repair. \\
    \hline
    At most two repair rounds &
      The bound keeps execution cost and the evaluation procedure
      reproducible while allowing one newly exposed dependency error to be
      considered (\Cref{sec:m-fixapply-round2}) &
      A notebook that reveals another problem after Round~2 is not fully
      recovered within this pipeline run. \\
    \hline
    One structured row for every repair decision &
      Recording decisions, evidence, abstentions, and Docker outcomes makes
      the evaluation denominators and individual traces inspectable
      (\Cref{sec:m-resultlogger}) &
      The trace is more detailed than a simple list of successful fixes and
      requires structured storage and export. \\
    \hline
    Targeted-error resolution and full recovery are reported separately &
      Removing the original dependency error and completing the whole
      notebook answer different questions, as the worked example shows
      (\Cref{sec:m-worked-example}) &
      The results need more than one success measure, but they avoid
      overstating a local repair as complete notebook recovery. \\
    \hline
\end{longtable}
